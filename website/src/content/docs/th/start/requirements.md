VPS เครื่องเดียวรันได้ทั้งเว็บ บนเครื่องนั้น Docker Compose จะรันคอนเทนเนอร์สามตัว คือแอป TomeCMS, PostgreSQL 17 และ SeaweedFS ซึ่งเก็บไฟล์มีเดียและรับคำสั่งแบบ S3 ส่วน TLS คุณต้องตั้ง reverse proxy ไว้ด้านหน้าเอง

## ขนาดเซิร์ฟเวอร์

| | ขั้นต่ำ | แนะนำ |
| --- | --- | --- |
| CPU | 1 vCPU | 2 vCPU |
| หน่วยความจำ | 2 GB พร้อม swap 2 GB | 4 GB |
| ดิสก์ | SSD 25 GB | SSD 50 GB และมากกว่านี้ถ้าคลังไฟล์ใหญ่ |
| สถาปัตยกรรม | `amd64` หรือ `arm64` | `amd64` หรือ `arm64` |
| ระบบ | Linux 64 บิตที่มี systemd, Docker Engine พร้อมปลั๊กอิน Compose, Node.js 22.12 ขึ้นไป และ Git | Ubuntu 24.04 LTS ซึ่งเป็นระบบที่ CI ใช้ |

สคริปต์ deploy ต้องการ Linux, Node.js และ Docker และต้องรันด้วยผู้ใช้ที่สั่ง `docker` ได้ ส่วนการติดตั้งแบบ managed ที่วางแผนไว้ใน 1.0.0 ต้องมี systemd 235 ขึ้นไปด้วย

### ทำไมต้องใช้หน่วยความจำเท่านี้

ตัวเลขเหล่านี้มาจากการวัดโค้ดเวอร์ชัน 0.7.0 บนเว็บเปล่าที่ยังไม่มีเนื้อหา ไม่ใช่เว็บที่มีคนใช้งานจริง หลังรับคำขอไปไม่กี่ร้อยครั้ง แอปใช้หน่วยความจำราว 180 MB, PostgreSQL ราว 75 MB และ SeaweedFS ราว 90 MB

หน่วยความจำขึ้นสูงสุดตอน build สคริปต์ deploy ในตอนนี้ build image ของแอปบนเซิร์ฟเวอร์เอง และตอนอัปเกรดก็ build ไปพร้อมกับที่เว็บยังเปิดให้บริการอยู่ แค่ `npm run build` อย่างเดียวก็ใช้ไปราว 700 MB ทั้งที่มี cache อยู่แล้วและรัน `npm ci` เสร็จไปก่อน การ build ครั้งแรกบนเซิร์ฟเวอร์ใหม่อาจใช้มากกว่านั้นอีก เซิร์ฟเวอร์ 1 GB จึงไม่พอ และขั้นต่ำจึงเป็น 2 GB พร้อม swap

ตอนอัปโหลดรูป เซิร์ฟเวอร์ต้องใช้หน่วยความจำเพิ่มอีกชั่วครู่เพื่อตรวจไฟล์ ส่วนนี้ยังไม่ได้วัด และอย่าลืมเผื่อให้ระบบปฏิบัติการกับ TLS proxy ด้วย

### ทำไมต้องใช้ดิสก์เท่านี้

image ของ PostgreSQL กับ SeaweedFS รวมกันราว 1.1 GB และ image ของแอปอีกหลายร้อย MB การ build แต่ละครั้งทิ้ง cache ไว้ขนาดใกล้เคียงกัน ซึ่งเรียกพื้นที่คืนได้ด้วย `docker builder prune`

ไฟล์มีเดียเก็บไว้ที่เดียวคือ SeaweedFS แต่การสำรองข้อมูลแบบเต็มจะคัดลอกฐานข้อมูลและไฟล์มีเดียทุกไฟล์ซ้ำอีกชุด ให้เผื่อพื้นที่เท่ากับขนาดไฟล์มีเดียคูณจำนวนชุดสำรองที่เก็บไว้บนเครื่อง หรือย้ายชุดสำรองไปเก็บที่อื่น การติดตั้งแบบ managed (1.0.0 เป็นต้นไป) จะสำรองข้อมูลก่อนอัปเดตทุกครั้งและไม่ลบชุดเก่าทิ้งเอง

## HTTPS origin สองชุด

เว็บหนึ่งเว็บต้องมีสอง origin ที่เป็น HTTPS ทั้งคู่ และต้องชี้ DNS มาที่เซิร์ฟเวอร์ให้เรียบร้อยก่อนติดตั้ง

- origin ของ CMS เช่น `https://cms.example.com` เป็นที่ที่ผู้อ่านและแอดมินเข้ามา
- origin ของมีเดีย เช่น `https://media.example.com` เป็น endpoint S3 ที่ให้บริการไฟล์

มีเดียต้องมี origin แยก เพราะเบราว์เซอร์อัปโหลดไฟล์ตรงเข้า bucket และผู้อ่านก็โหลดรูปจากที่นี่ สคริปต์ deploy รับเฉพาะ HTTPS บนชื่อโฮสต์สาธารณะสำหรับทั้งสอง origin และจะไม่รับชื่อในเครื่องอย่าง `localhost`, IP ในวงภายใน หรือโดเมนสำหรับทดสอบ

## ตั้ง reverse proxy

proxy และใบรับรองเป็นส่วนที่คุณต้องเตรียมเอง ตั้งให้แต่ละ origin ส่งต่อไปที่พอร์ตของตัวเองบนเซิร์ฟเวอร์

| Origin | ส่งต่อไปที่ |
| --- | --- |
| CMS `https://cms.example.com` | `127.0.0.1:4321` |
| มีเดีย `https://media.example.com` | `127.0.0.1:9000` |

การตั้งค่า proxy สองข้อมีผลกับการอัปโหลด ข้อแรก origin ของมีเดียต้องส่ง header `Host` ต่อไปตามเดิมโดยไม่แก้ เพราะที่อยู่สำหรับอัปโหลดแต่ละครั้งถูกเซ็นไว้กับชื่อโฮสต์นั้น ข้อที่สอง ต้องรับ request body ได้ถึง 25 MB ซึ่งเป็นขนาดเอกสารใหญ่สุดที่คลังไฟล์รับ (รูปรับได้ถึง 8 MB) proxy บางตัวส่งชื่อโฮสต์ของตัวเองต่อไป หรือจำกัด body ไว้ที่ 1 MB ถ้าไม่ได้ตั้งค่าเพิ่ม nginx เป็นแบบนั้นทั้งสองข้อ

## พอร์ตและไฟร์วอลล์

Compose ผูก PostgreSQL (`5432`), SeaweedFS (`9000`) และแอป (`4321`) ไว้กับ `127.0.0.1` เท่านั้น จากภายนอกจึงเข้าถึงได้ผ่าน proxy ทางเดียว ไฟร์วอลล์เปิดแค่ SSH, HTTP และ HTTPS ก็พอ

สคริปต์ติดตั้งไม่แตะไฟร์วอลล์และไม่ขอใบรับรองให้ ทั้งสองอย่างนี้คุณต้องตั้งเอง
