เว็บที่ใช้ TomeCMS เก็บเนื้อหาไว้สองที่ บทความ เพจ การตั้งค่า และข้อมูลการเข้าสู่ระบบอยู่ใน PostgreSQL ส่วนไฟล์ในคลังไฟล์ รวมถึงโลโก้ เป็น object อยู่ใน bucket ของมีเดีย การสำรองแค่ฐานข้อมูลจึงไม่ครบ `npm run backup` จะคัดลอกทั้งสองที่ในการรันครั้งเดียว โดยทำตอนที่แอปหยุดอยู่ ข้อมูลสองฝั่งจึงตรงกัน

## ก่อนสำรองข้อมูลครั้งแรก

คำสั่งสำรองข้อมูลและคำสั่งตรวจการกู้คืนรันบนเซิร์ฟเวอร์จากโฟลเดอร์โค้ดด้วย Node.js สคริปต์ deploy สร้างแอปไว้ใน Docker และไม่ได้ติดตั้งแพ็กเกจที่สองคำสั่งนี้ต้องใช้ลงในโฟลเดอร์โค้ด จึงต้องติดตั้งเองหนึ่งครั้ง

```sh
npm ci
```

ทั้งสองคำสั่งอ่าน `.env.local` จากโฟลเดอร์โค้ด คำสั่งสำรองข้อมูลเข้าถึง PostgreSQL ผ่าน Compose และเข้าถึง bucket ผ่าน `S3_INTERNAL_ENDPOINT` ถ้าตั้งไว้ และผ่าน `S3_ENDPOINT` ถ้าไม่ได้ตั้ง ดังนั้นทั้งสอง service และ proxy ของ origin มีเดีย (หรือที่อยู่ภายใน) ต้องทำงานอยู่ คำสั่งเหล่านี้รันบนเครื่อง host เอง `S3_INTERNAL_ENDPOINT` ใน `.env.local` จึงต้องเป็นที่อยู่ที่ host เข้าถึงได้ เช่น `http://127.0.0.1:9000` เพราะ `http://seaweedfs:8333` ใช้ได้เฉพาะภายในเครือข่าย Docker ของการติดตั้งแบบ managed

## สำรองข้อมูล

หยุดแอปก่อน เพื่อไม่ให้มีอะไรเขียนข้อมูลระหว่างคัดลอก

```sh
docker compose -f compose.yaml --env-file .env.local stop app
```

แล้วสำรองไปไว้ในโฟลเดอร์ที่อยู่นอกโฟลเดอร์โค้ด

```sh
npm run backup -- --offline --output-root "$HOME/tomecms-backups"
```

ต้องใส่ `--offline` ทุกครั้ง เป็นการยืนยันว่าไม่มีอะไรเขียนข้อมูลอยู่ และคำสั่งจะไม่ยอมเริ่มถ้าคอนเทนเนอร์แอปยังทำงานอยู่ เมื่อเสร็จแล้วจะพิมพ์ว่าชุดสำรองอยู่ที่ไหนและมีข้อมูลเท่าไร

```text
Backup complete: /home/deploy/tomecms-backups/tomecms-20260913T120000000Z
Database records: 42; media objects: 118
```

ตัวเลขแรกคือจำนวนบทความกับเพจรวมกัน เมื่อเสร็จแล้วให้เปิดแอปอีกครั้ง เว้นแต่คุณกำลังจะ[อัปเดต](/tome-cms/th/running/updating/)ต่อ

```sh
docker compose -f compose.yaml --env-file .env.local start app
```

ถ้าใน bucket มี object ที่ TomeCMS ไม่ได้เป็นคนตั้งชื่อ คำสั่งจะหยุดพร้อมข้อความ `The media bucket contains an unsupported object key.` ให้ย้าย object เหล่านั้นออกจาก bucket แล้วรันใหม่

## ในชุดสำรองมีอะไรบ้าง

การรันแต่ละครั้งจะสร้างโฟลเดอร์ใหม่หนึ่งโฟลเดอร์ใต้ output root ตั้งชื่อตามเวลาที่เริ่มรันเป็น UTC เช่น `tomecms-20260913T120000000Z` ข้างในมี

| ไฟล์หรือโฟลเดอร์ | คืออะไร |
| --- | --- |
| `database.dump` | ฐานข้อมูล `tomecms` ทั้งหมด dump ด้วย `pg_dump` ในรูปแบบ custom โดยไม่มีข้อมูล owner และสิทธิ์ |
| `objects/` | object ทุกตัวใน bucket วางไว้ที่ path เดียวกับ key ของมัน |
| `manifest.json` | เวอร์ชันของ TomeCMS ที่สร้างชุดสำรอง ที่อยู่ของเว็บ ชื่อฐานข้อมูลและชื่อ bucket จำนวนการตั้งค่า บทความ เพจ และรายการในคลังไฟล์ที่ฐานข้อมูลมีตอนนั้น checksum SHA-256 ของไฟล์ dump และ checksum, content type และขนาดของ object แต่ละตัว |

คำสั่งเขียน `manifest.json` เป็นไฟล์สุดท้าย ถ้าโฟลเดอร์ไหนไม่มีไฟล์นี้ แปลว่าการสำรองครั้งนั้นล้มเหลวหรือถูกขัดจังหวะ ห้ามนำไปกู้คืน

`--database-only` จะไม่สำรอง bucket โฟลเดอร์จะไม่มี `objects/` และ manifest จะมี `"scope": "database"` โดยไม่มีรายการไฟล์ ตัวอัปเดตใช้แบบนี้ก่อนการอัปเดตที่ไม่มี migration ตั้งแต่ 1.3.0 เพราะการอัปเดตแบบนั้นไม่เปลี่ยนตารางและไม่ได้คาดว่าจะเขียนไฟล์ใหม่ ถ้าจะกู้คืนจากชุดแบบนี้ ให้กู้ dump แล้วปล่อย bucket ไว้อย่างเดิม คำสั่งตรวจชุดสำรองใช้ได้กับทั้งสองแบบ และบอกว่าตรวจแบบไหน

ชุดสำรองไม่ได้เก็บค่าลับใน `.env.local` ไว้เลย เว็บที่กู้คืนจากชุดสำรองต้องใช้ค่าลับชุดเดิม จึงต้องเก็บสำเนา `.env.local` ไว้ในที่ปลอดภัย แยกจากชุดสำรอง ตามที่อธิบายไว้ในหน้า[การตั้งค่า](/tome-cms/th/running/configuration/) แต่ไฟล์ dump ยังมีทุกอย่างในฐานข้อมูล รวมถึงข้อมูลการเข้าสู่ระบบ จึงต้องเก็บชุดสำรองให้มิดชิดเท่ากับไฟล์นั้น การกู้คืนลงเซิร์ฟเวอร์เครื่องอื่นจะใช้ความลับของเซิร์ฟเวอร์เครื่องนั้นเอง ด้วยเหตุนี้การ[ย้ายเว็บ](#ย้ายไปเซิร์ฟเวอร์เครื่องใหม่)จึงจบด้วยรายการตรวจ

## ไฟล์ไปอยู่ที่ไหน

`--output-root` ต้องเป็น absolute path ที่อยู่นอกโฟลเดอร์โค้ด คำสั่งไม่รับ path แบบ relative, path ในโฟลเดอร์โค้ด และ root ของระบบไฟล์ ถ้าโฟลเดอร์ยังไม่มี คำสั่งจะสร้างให้ โฟลเดอร์ในชุดสำรองตั้งสิทธิ์ให้เจ้าของเข้าถึงได้คนเดียว (`0700`) และไฟล์ก็เช่นกัน (`0600`)

ชุดสำรองที่อยู่บนดิสก์ของเซิร์ฟเวอร์เองจะหายไปพร้อมดิสก์นั้น จึงควรคัดลอกแต่ละชุดไปเก็บไว้ที่เครื่องอื่น และเพราะแต่ละชุดคัดลอกทั้งฐานข้อมูลและทุกไฟล์ใน bucket ซ้ำอีกรอบ ให้เผื่อพื้นที่ดิสก์ตามจำนวนชุดที่เก็บไว้บนเซิร์ฟเวอร์

## ตรวจชุดสำรอง

ตรวจชุดสำรองทุกชุดก่อนนำไปใช้จริง คำสั่งตรวจการกู้คืนจะกู้ชุดสำรองลงใน Compose project แยกที่ใช้แล้วทิ้ง แล้วเทียบผลกับ manifest

```sh
npm run restore:check -- \
  --backup /home/deploy/tomecms-backups/tomecms-20260913T120000000Z \
  --project tomecms-restore-check-20260913
```

`--backup` คือ absolute path ของชุดสำรอง `--project` คือชื่อ project ที่ใช้แล้วทิ้ง ต้องขึ้นต้นด้วย `tomecms-restore-check-` แล้วตามด้วยตัวพิมพ์เล็ก ตัวเลข หรือขีดกลางไม่เกิน 40 ตัว โดยขึ้นต้นและลงท้ายด้วยตัวอักษรหรือตัวเลข ใช้ชื่อใหม่ทุกครั้ง เพราะคำสั่งจะไม่ยอมใช้ project ที่มีคอนเทนเนอร์อยู่แล้ว และจะไม่แตะ project ของเว็บจริงเลย

คำสั่งทำงานตามลำดับนี้

1. ตรวจไฟล์ dump และ object ทุกตัวกับ checksum ใน manifest
2. เปิด PostgreSQL และ SeaweedFS ชุดของตัวเองที่พอร์ต `55432` และ `59000` บน `127.0.0.1` ระหว่างที่คำสั่งทำงานต้องปล่อยสองพอร์ตนี้ให้ว่าง
3. กู้ไฟล์ dump ลงใน PostgreSQL ชุดนั้น
4. ใส่ object ทุกตัวกลับเข้าไปพร้อม content type เอกสารแต่ละไฟล์จะได้ header `Content-Disposition` คืนมาด้วย ซึ่งเป็น header ที่กำหนดชื่อไฟล์ตอนดาวน์โหลด และกำหนดว่า PDF จะเปิดในเบราว์เซอร์หรือไม่ header นี้ติดอยู่กับ object ใน bucket และชุดสำรองไม่ได้เก็บไว้ คำสั่งจึงสร้างขึ้นใหม่จากแถวของเอกสารนั้นใน `media_items`
5. เทียบจำนวนการตั้งค่า บทความ เพจ และรายการในคลังไฟล์ที่กู้คืนได้กับตัวเลขใน manifest และเทียบ object ที่กู้คืนได้กับรายการใน manifest
6. ลบคอนเทนเนอร์และ volume ที่ใช้แล้วทิ้งออก ไม่ว่าการตรวจจะผ่านหรือไม่

ชุดสำรองที่ผ่านจะจบด้วย `Restore verified in disposable project tomecms-restore-check-20260913.` ถ้าไม่ผ่าน บรรทัดสุดท้ายจะขึ้นต้นด้วย `Error:` เช่น `Database dump checksum does not match its manifest.` หรือ `Restored object inventory does not match the backup.` อย่าใช้ชุดสำรองที่ตรวจไม่ผ่าน

## กู้คืนเว็บ

บนเซิร์ฟเวอร์แบบ managed ตั้งแต่ 1.13.0 คำสั่ง `sudo tome restore` ใส่ชุดสำรองกลับเข้าเว็บ คำสั่งจะสำรองเว็บตามสภาพปัจจุบันไว้ก่อน แล้วจึงแทนที่ฐานข้อมูล และถ้าเป็นชุดสำรองเต็มก็แทนที่มีเดียด้วย ถ้าขั้นใดล้มเหลว จะใส่ชุดสำรองเพื่อความปลอดภัยนั้นกลับ เว็บที่กู้คืนไปครึ่งหนึ่งจึงไม่ถูกนำมาให้บริการเลย

```sh
sudo tome restore /var/backups/tome-cms/tomecms-20261001T100000000Z
```

ชุดสำรองต้องอยู่ตรง ๆ ใน `/var/backups/tome-cms` และต้องสร้างไว้สำหรับที่อยู่ของเว็บนี้ โดย TomeCMS รุ่นนี้หรือรุ่นเก่ากว่า ชุดสำรองที่มีลิงก์หรือไฟล์พิเศษอยู่ข้างในจะถูกปฏิเสธ `tome restore` เปลี่ยนเจ้าของของชุดสำรองเป็นผู้ใช้ของตัวอัปเดต เพราะตัวอัปเดตรันด้วยผู้ใช้นั้น หน้า[คำสั่ง tome](/tome-cms/th/running/cli/#tome-restore)แสดงขั้นตอน กรณีที่ปฏิเสธทุกแบบ และสิ่งที่เกิดขึ้นเมื่อขั้นใดล้มเหลว หลังกู้คืนทุกคนจะถูกออกจากระบบ คุณจึงต้องเข้าสู่ระบบใหม่ด้วย passkey และชุดสำรองเพื่อความปลอดภัยจะอยู่ใน `/var/backups/tome-cms/` จนกว่าคุณจะลบเอง

เซิร์ฟเวอร์ต้องมีแอป 1.13.0 และตัวอัปเดต 1.6.0 คำสั่ง `sudo npm run updater:upgrade` จาก checkout ของ v1.13.0 ติดตั้งตัวอัปเดตและ `tome` ตัวใหม่ไปพร้อมกัน ตามที่หน้า[การอัปเดต](/tome-cms/th/running/updating/#อัปเกรดตัวอัปเดต)แสดงไว้ การ build จาก source ไม่มี `tome` ต้องกู้คืนเอง โดยหยุดแอปไว้ก่อน ทำแบบเดียวกับที่คำสั่งตรวจการกู้คืนทำ

- กู้ `database.dump` ลงใน PostgreSQL ของเว็บด้วย `pg_restore`
- ใส่ทุกไฟล์ใต้ `objects/` กลับเข้า bucket ที่ key เดิม พร้อม content type ตามที่ manifest บันทึกไว้
- ใส่ header `Content-Disposition` ให้เอกสารทุกไฟล์ โดยสร้างแบบเดียวกับที่ `contentDisposition` ใน `src/server/media/disposition.ts` สร้างจากชื่อและชนิดของเอกสารใน `media_items` ถ้าไม่มี header นี้ เอกสารจะไม่ได้ดาวน์โหลดด้วยชื่อของมันเอง
- เปิดแอปด้วย `.env.local` ชุดที่เว็บใช้อยู่ตอนสำรองข้อมูล

ลองกู้คืนบนเซิร์ฟเวอร์สำรองก่อนถึงวันที่ต้องใช้จริง และเก็บข้อมูลเดิมไว้จนกว่าเว็บที่กู้คืนแล้วจะใช้งานได้

## ย้ายไปเซิร์ฟเวอร์เครื่องใหม่

โดเมนยังเป็นโดเมนเดิมเมื่อคุณย้าย passkey จึงยังใช้ได้ การกู้คืนจะปฏิเสธชุดสำรองที่มาจากที่อยู่อื่น

1. บนเซิร์ฟเวอร์เครื่องเก่า สำรองข้อมูลเต็มชุด คำสั่งจะบอกว่าบันทึกไว้ที่ไหน

   ```sh
   sudo tome backup --full
   ```

2. ติดตั้ง TomeCMS บนเซิร์ฟเวอร์เครื่องใหม่ด้วยโดเมนเดียวกัน ที่รุ่นเดียวกับเว็บเดิมหรือใหม่กว่า ตามที่หน้า[ติดตั้งบน VPS](/tome-cms/th/start/install/)อธิบายไว้ `tome restore` จะปฏิเสธชุดสำรองที่สร้างไว้สำหรับที่อยู่อื่นหรือสร้างโดยรุ่นที่ใหม่กว่า
3. คัดลอกชุดสำรองเข้า `/var/backups/tome-cms` บนเซิร์ฟเวอร์เครื่องใหม่ ในฐานะ root ด้วย `rsync -a` ซึ่งเก็บโฟลเดอร์ไว้ตามเดิม

   ```sh
   sudo rsync -a /var/backups/tome-cms/tomecms-20261003T110000000Z \
     root@new.example.com:/var/backups/tome-cms/
   ```

   สำเนาต้องไปอยู่ตรง ๆ ในโฟลเดอร์นั้น ไม่ใช่ในโฟลเดอร์ย่อยข้างใน `rsync -a` คงเจ้าของเดิมจากเครื่องเก่าไว้ และ `tome restore` จะตั้งเจ้าของให้เป็นผู้ใช้ของตัวอัปเดตไม่ว่าเดิมจะเป็นใคร
4. บนเซิร์ฟเวอร์เครื่องใหม่ กู้คืนชุดสำรอง

   ```sh
   sudo tome restore /var/backups/tome-cms/tomecms-20261003T110000000Z
   ```

5. ชี้ DNS ของโดเมนมาที่เซิร์ฟเวอร์เครื่องใหม่ เข้าสู่ระบบด้วย passkey แล้วไล่ตามรายการตรวจด้านล่าง

สิ่งที่เขียนบนเซิร์ฟเวอร์เครื่องเก่าหลังขั้นที่ 1 จะไม่อยู่ในชุดสำรอง จึงควรหยุดเขียนที่นั่นหลังสำรองเสร็จ

### หลังย้ายเสร็จ

- **เข้าสู่ระบบใหม่** การกู้คืนทำให้ทุกคนออกจากระบบ passkey ของคุณใช้ได้ เพราะโดเมนไม่เปลี่ยน
- **ใส่ความลับของปลั๊กอินใหม่** ความลับถูกเข้ารหัสด้วย `TOME_CMS_CONTEXT_SECRET` ของเซิร์ฟเวอร์เอง และไม่มีความลับใดถูกย้ายข้ามเซิร์ฟเวอร์ ถ้าความลับที่กู้คืนมาเปิดบนเครื่องนี้ไม่ได้ `tome restore` จะบอกว่าปลั๊กอินไหน ตั้งค่าตัวไหน แล้วคุณใส่ใหม่ในเมนู "ปลั๊กอิน"
- **สร้างรหัสกู้คืนชุดใหม่** รหัสเดิมสร้างด้วย `TOME_CMS_RECOVERY_PEPPER` ของเซิร์ฟเวอร์เครื่องเก่า จึงใช้ไม่ได้ ให้สร้างชุดใหม่ในเมนู "ความปลอดภัย"
- **ดูเว็บ** เปิดบทความที่มีรูปสักสองสามรายการ ดาวน์โหลดไฟล์หนึ่งไฟล์ และเปิดเมนู "ระบบ" ก่อนปิดเซิร์ฟเวอร์เครื่องเก่า

`tome restore` จะแสดงข้อที่สองและสามเองเมื่อเข้าเงื่อนไข และถ้าชุดสำรองไม่มีความลับของปลั๊กอินเลย จะบอกให้สร้างรหัสกู้คืนชุดใหม่เผื่อว่าชุดสำรองมาจากเซิร์ฟเวอร์อื่น

## สำเนาข้อความของคุณเป็น Markdown

`sudo tome export` เขียนบทความและเพจทุกรายการ พร้อมมีเดียที่ใช้ ลงใน `/var/backups/tome-cms/markdown-<time>.tar.gz` และ `sudo tome import` เพิ่มรายการเหล่านั้นเข้าเว็บ มันคือสำเนาที่คุณอ่านเอง เก็บไว้เอง หรือย้ายเข้าเว็บ TomeCMS อื่นได้ ไม่ใช่ชุดสำรอง เพราะกู้การตั้งค่าหรือบัญชีของคุณคืนไม่ได้

ในไฟล์มีบทความและเพจทุกรายการ ทุกภาษา ทุกสถานะ และมีเดียที่รายการเหล่านั้นอ้างถึง ส่วนที่ไม่รวมคือการตั้งค่า เมนู สไลด์ การเปลี่ยนเส้นทาง บัญชี และสถิติ ซึ่ง `tome restore` นำกลับมาจากชุดสำรอง และไฟล์ในคลังไฟล์ที่ไม่มีอะไรใช้ ซึ่งชุดสำรองเต็มเก็บไว้ ระหว่างที่เขียนไฟล์ เว็บเปิดอยู่

```text
manifest.json
posts/en/hello.md
posts/en/hello.tome.json
pages/th/about.md
pages/th/about.tome.json
media/<object key>
```

- **`manifest.json`** บอกว่านี่คือไฟล์ Markdown ของ TomeCMS สร้างเมื่อไรและโดยรุ่นไหน สำหรับที่อยู่ไหน มีบทความ เพจ และไฟล์มีเดียอย่างละกี่รายการ และชื่อ ชนิด checksum และขนาดของแต่ละไฟล์ ตั้งแต่ 1.20.0 ยังมี `categories` ซึ่งเก็บชื่อใน URL และคำอธิบายทั้งสองภาษาของทุกหมวดหมู่ที่บทความอยู่ ยกเว้นหมวดเริ่มต้น
- **ไฟล์ `.md` แต่ละไฟล์** คือข้อความสำหรับอ่าน front matter มี `title`, `slug`, `language`, `status`, `published` และ `planned` เมื่อมีค่า, `updated`, `categories` ของบทความตามชื่อ, `excerpt`, `cover`, `show_cover`, `meta_title`, `meta_description` และ `translation` ซึ่งเป็นค่าเดียวกันในทุกภาษาของรายการที่แปลไว้ เนื้อความเป็น Markdown และรูปกับลิงก์ไฟล์ชี้เข้าไปที่ `media/` บล็อกที่ Markdown เก็บไม่ได้ เช่นวิดีโอ ไฟล์แนบ หรือตารางที่มีเซลล์ผสาน จะกลายเป็นลิงก์ธรรมดาหรือบรรทัดสั้น ๆ ที่บอกชื่อ สี ขีดเส้นใต้ และการจัดตำแหน่งข้อความจะไม่อยู่ใน `.md`
- **ไฟล์ `.tome.json` แต่ละไฟล์** เก็บเอกสารของตัวแก้ไขไว้ตามจริง โดยลิงก์มีเดียชี้เข้าไปที่ `media/` การนำเข้าจะใช้ไฟล์นี้เมื่อมี สิ่งที่ `.md` แสดงไม่ได้จึงไม่หายไป `tome export` จะบอกตอนจบว่ามีกี่รายการที่มีการจัดรูปแบบแบบนั้น

ถ้าจะนำข้อความเข้ามา ให้รัน `sudo tome import` กับไฟล์นั้น ตามที่หน้า[คำสั่ง tome](/tome-cms/th/running/cli/#tome-import)อธิบายไว้ คำสั่งจะไม่เขียนทับรายการที่เว็บมี address นั้นอยู่แล้ว คุณเขียนไฟล์เองก็ได้ ขอแค่ไฟล์ `.md` มี title วางไว้ที่ `posts/en/<slug>.md` หรือ `pages/th/<slug>.md`
