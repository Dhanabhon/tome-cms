# TomeCMS 1.12.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** add three Tome CLI commands for building themes and plugins in a source checkout:
`tome theme new`, `tome plugin new` and `tome check`. `tome check` runs in `npm run check`.
Ships as 1.12.0.

**Architecture:** the commands live in the existing `src/cli/` program, as a second group:
- they need no root, and run only inside a TomeCMS checkout found by walking up from the cwd;
- the pure logic (id rules, renames, anchor edits, check rules) sits in small modules that the
  tests drive against temporary directories;
- the commands are thin wrappers over those modules.

**Tech Stack:** Node 22, TypeScript, `tsx`, `node:test`, Astro (`astro check` for the build
proof).

**Spec:** `docs/specs/2026-10-03-tome-cli-builders-design.md`.

## Global Constraints

- **Git:**
  - never stash;
  - stage by explicit path;
  - commit with `git commit -F <file> -- <paths>` as its own command;
  - no attribution lines;
  - never push or merge.
- **No migration.** No change to the updater. `UPDATER_VERSION` stays `1.5.0`.
- **Ids:** `^[a-z][a-z0-9]{1,30}$`. An id is refused when its directory exists, or when it is
  already listed in that kind's `manifests.ts` or `registry.ts`.
- **Running:**
  - The run is `npm run tome -- <command>`: a new `package.json` script that runs
    `src/cli/main.ts` through `tsx`.
  - The builder commands need no root.
  - Outside a checkout they print "Run this in a TomeCMS source checkout" and exit 1. A checkout is
    a dir whose `package.json` name is `tome-cms` and which has `src/themes/manifests.ts`.
  - The server commands keep their root check, unchanged.
  - Exit codes: 0 for success, 1 for a failure or refusal, 2 for usage. `--help` works for every
    command.
- **Anchor edits:**
  - insert at known anchors in `src/themes/manifests.ts`, `src/themes/registry.ts`,
    `src/plugins/manifests.ts` and `src/plugins/registry.ts`;
  - on a missing or ambiguous anchor, change nothing, print the lines to add by hand, and exit 1;
  - the order of work is: check the id, check the anchors, write the directory, then edit;
  - if an edit fails, remove the new directory;
  - `--dry-run` writes nothing.
- **Renames** follow explicit rules: the manifest id, the class prefixes `<from>-` → `<id>-`, and
  `body` or data attributes carrying the id. Prose and comments mentioning the source theme are
  left alone. The manifest name and description become the id, in en and th.
- **Skeletons** take their shapes from `src/themes/contract.ts` and `src/plugins/contract.ts`. A
  plugin skeleton returns safe defaults, so it does nothing until it is written.
- **`tome check` rules (spec 1–7):**
  - it reuses the existing logic for "no server imports in themes", from
    `tests/unit/theme-registry.test.ts` around line 52;
  - it reuses the logic for "no raw colour outside token blocks", from
    `tests/unit/almanac-tokens.test.ts` around line 118, generalised;
  - each problem is reported as `path:line: what is wrong`;
  - `npm run check` runs it.
- **English output** only. Docs in en and th.
- **Tests:**
  - unit tests with `node --import tsx --test`, against temporary copies, never touching the
    working tree;
  - no test may depend on machine paths or the time zone.

## Review Focus

1. **A rename must not corrupt the copied theme.** Copying `almanac` must produce a theme that
   builds and keeps Almanac's look. That covers its fonts link and its `body.almanac` selectors,
   which become `<id>`. A word like "Plain" in a comment must not change. Task 2's build proof
   covers this.
2. **The four list files must never be left half-edited.**
   - an unexpected shape refuses;
   - a failure after the directory is written removes the directory;
   - two runs with the same id refuse the second.

   Tested in Task 1.
3. **`tome check` must pass on today's repository** (all three themes, all six plugins), or each
   difference must be fixed or ruled on before it joins `npm run check`. Task 3.
4. **The builder commands must never run as part of the server's `tome`** in a way that writes
   anywhere. Outside a checkout they refuse before touching the filesystem. Task 1.
5. **A generated plugin must type-check against the contract for every hook choice,** and must
   not change any page while it is switched off. Task 2's build proof covers this, by switching it
   on in a test where cheap.

### Task 1: The checkout, ids and anchor edits (`src/cli/build/`)

**Files:**
- Create:
  - `src/cli/build/checkout.ts`: `findCheckout(cwd): string | null`;
  - `src/cli/build/ids.ts`: `validateId(kind, id, root): { ok: true } | { ok: false, reason }`;
  - `src/cli/build/anchors.ts`: `planRegistration(kind, id, root)` returns
    `{ ok: true, edits: FileEdit[] } | { ok: false, manualLines: string[] }`, and
    `applyEdits(edits)`. The edits are pure text in and text out, with the anchors documented.
- Modify:
  - `src/cli/args.ts` and `src/cli/main.ts`: route `theme`, `plugin` and `check`; the builder
    group skips the root check;
  - `package.json`: add the `tome` script.
- Test:
  - `tests/unit/cli-build-checkout.test.ts`;
  - `tests/unit/cli-build-ids.test.ts`;
  - `tests/unit/cli-build-anchors.test.ts`. It uses copies of the real four list files as
    fixtures, read at test time from the repo, plus hand-broken variants.

- [ ] **Step 1: Tests.**
  - `findCheckout`: inside the repo, in a subdirectory, and outside, which gives null.
  - Ids: valid ids; invalid ones (uppercase, a hyphen, a leading digit, too long); one that is
    taken by a directory or by a list entry.
  - Anchors:
    - the exact expected new text of all four files, for a theme and for a plugin;
    - the registry's alphabetical insertion;
    - a missing anchor or a duplicate anchor gives the manual lines and changes nothing.
  - Parsing: `theme new`, `plugin new` and `check` parse without root; server commands still
    demand root.
- [ ] **Step 2: Implement.**
- [ ] **Step 3: Run** `npm run check` and the unit tests.
  Commit: `feat: tome finds a source checkout and can register a theme or plugin safely`.

### Task 2: `tome theme new` and `tome plugin new`

**Files:**
- Create:
  - `src/cli/build/theme.ts`: the copy and rename rules, as pure functions over a file's path and
    text;
  - `src/cli/build/plugin.ts`: the skeleton text for each hook, and `--client`;
  - `src/cli/commands/theme-new.ts` and `src/cli/commands/plugin-new.ts`, which run the flow:
    validate, plan the anchors, write the directory, apply the edits, roll back on failure, and
    support `--dry-run`.
- Test:
  - `tests/unit/cli-build-theme.test.ts`;
  - `tests/unit/cli-build-plugin.test.ts`;
  - `tests/integration/cli-build-generate.test.ts`. This is the build proof:
    1. copy the repo's `src/`, `package.json`, the tsconfigs and `astro.config.*` into a temp dir,
       symlinking `node_modules`;
    2. run `theme new zzdemo --from almanac`, `theme new zzplain`, and
       `plugin new zzpub --hook publicPage --client`;
    3. run `astro check` in the temp dir and expect 0 errors;
    4. run `tome check` there and expect it to pass;
    5. delete the dir.

    If `astro check` in a copy proves too slow or fragile, make it a CI-only step, and say so in
    the report.

- [ ] **Step 1: Unit tests for the rename rules,** on real theme files read from the repo:
  - the manifest `id` and name;
  - class prefixes in CSS and in `.astro`;
  - `body` class or data attribute;
  - comments and prose left alone;
  - the fonts link kept as a path to the same files.

  Unit tests for the plugin skeleton per hook: it matches the contract shape, and `--client`
  writes `client.ts`. Flow tests: `--dry-run` writes nothing; a forced failure in the edit step
  removes the directory.
- [ ] **Step 2: Implement.**
- [ ] **Step 3: Write the build proof** integration test.
- [ ] **Step 4: Run** `npm run check`, the unit tests and the integration test.
  Commit: `feat: tome theme new and tome plugin new start a theme or plugin from a working one`.
