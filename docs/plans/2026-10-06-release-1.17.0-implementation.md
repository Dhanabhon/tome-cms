# Release 1.17.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the owner add a second device with a one-time link, move the Turnstile challenge off the passkey sign-in onto the recovery-code form, show where each passkey lives, and fix `prepare-vps.sh` under `sudo` from root.

**Architecture:** The device link is a third enrollment purpose, `device`, beside `install` and `recovery`, reusing the signed one-time context in `installation_enrollments` and better-auth's `registration.afterVerification`. The Security screen issues it after a fresh passkey check; `/add-device` registers a passkey with it and signs the new device in. Turnstile's server check moves from `[...all].ts` to `POST /api/recovery/start`. Provider names come from a static AAGUID map.

**Tech Stack:** Astro 7 SSR, React islands, better-auth 1.7 + `@better-auth/passkey`, Kysely/Postgres, node:test, Playwright with CDP virtual authenticators.

**Spec:** `docs/specs/2026-10-06-release-1.17.0-design.md` — read it; its rulings table is binding.

## Review Focus

1. A device link must never delete a passkey or a session; only recovery does. Test that every existing passkey survives a device registration.
2. A link must be spent by: use, creating a newer link, **Cancel link**, expiry. A second use of the same link fails with the expired message.
3. A stale session (older than 5 minutes) cannot create a link: `403` from the API.
4. The sign-in page sends no Turnstile token and `verify-authentication` is never refused for a missing one; `/api/recovery/start` is refused without a token when the plugin is on, and the recovery form never sends an empty token.
5. `/add-device` works in headless mode, during maintenance, and is not cached; `/add-device` cannot be chosen as the admin path.

**E2E (`tests/e2e/device-link.spec.ts`, desktop only, its own stack like `passkey-sign-in.spec.ts`):**
1. Context A signs in through recovery (one recovery sign-in), backdates its session 10 minutes, presses **Create a link** (the step-up passes with A's authenticator), reads the URL from the input, sees the QR image.
2. Context B (`browser.newContext()`) with its own virtual authenticator opens the URL, waits for hydration, presses **Create a passkey**, lands on `/admin`.
3. The database holds 2 passkeys; B has a session; A's passkey is untouched.
4. Opening the same URL in a fresh context C shows the expired message and no button.
5. A second link, then **Cancel link**, then opening it shows the expired message.
