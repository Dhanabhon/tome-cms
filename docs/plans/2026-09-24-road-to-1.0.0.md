# The road to 1.0.0

Date: 2026-09-24
Status: Agreed order of work; each step gets its own spec and plan where it needs one

1.0.0 is an update boundary before it is a feature set: the first managed-VPS installation that
can apply a verified update from the admin, `1.0.0 → 1.0.1` (see [releases/1.0.0.md](../releases/1.0.0.md)).
Its releases must be **public, published and immutable**, because the installer and updater
download the manifest and attestations from GitHub without a credential. The repository is
private today, so it has to open **before** `v1.0.0` is tagged, not after.

## Step 2, done on 2026-09-25

- **The secret scan.** Every blob reachable from any ref (2,954) and every commit message
  (572) was scanned. It found no credential; every hit was a placeholder or a test value. The
  deleted `supabase/` and `.hallmark/` files hold nothing sensitive either.
- **The docs.** All 68 files under `docs/` were read in full. The one finding that mattered was
  that the stack table and the overview diagram still said Novel, which left in 0.9.0; both now
  say Tiptap. What is left is the owner's choice to keep. The plans are written to an AI coding
  agent, some carry local paths such as `/Users/tom/...` and session scratchpad paths, and
  `DESIGN.md` keeps an "Agent Prompt Guide".
- **Commit emails.** The personal address is in the history, which stays as it is. New commits
  in this repository use the GitHub noreply address (`git config --local user.email`).
- **Files.** `SECURITY.md`, `CONTRIBUTING.md`, the issue forms, and a pull-request template.
- **The workflows.** They are already safe for pull requests from forks:
  - `pull_request`, not `pull_request_target`
  - a read-only token
  - no secrets
  - every third-party action pinned by SHA

## Right after step 3

GitHub offers none of these to a private repository on the free plan, so each waits for the
switch to public:

1. **A ruleset on `main`.** It blocks force-pushes and deletion, and requires the `verify`
   check before a pull request merges. The owner bypasses it, so a direct push to `main` still
   works.
2. **Actions.** Require approval before a workflow runs for a pull request from any outside
   contributor.
3. **Private vulnerability reporting**, which `SECURITY.md` points at, switched on.
4. **The owner's own GitHub email settings.** Keep the address private, and block
   command-line pushes that would expose it.
5. **At the first release**, the `tome-cms` container package on GHCR made public. The
   installer and updater pull the image without a credential.
