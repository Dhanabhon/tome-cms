# TomeCMS 1.13.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** three root commands on the server.
- `sudo tome restore <backup>` restores a backup into the site itself, through an updater job.
- `sudo tome export` writes every post and page as Markdown plus an exact `.tome.json`, with their
  media, into one archive.
- `sudo tome import <archive>` brings such an archive back in, keeping each item's status and
  dates, and never overwriting.

It ships as 1.13.0, with updater 1.6.0.

**Architecture:** three layers, each tested on its own.
1. **In the app image.** A new bundled entry, `dist/server/content-cli.mjs`, built by esbuild the way
   `dist/server/markdown-parse-worker.mjs` already is, and run as `npm run --silent content -- <step>`.
   - It does everything that needs the app's environment, database and bucket: the database and
     media restore steps, the after-restore report, export, and the import plan and apply.
   - It always runs as a `docker compose run --rm --no-deps` one-shot of the installed image, with a
     work directory mounted at `/work`. That is how the updater already runs backups and migrations.
2. **The updater (1.6.0).** It gains a restore job: verify, safety backup, restore, migrate, start,
   check, and roll back on failure. It orchestrates those one-shots under the shared lock and the
   maintenance marker.
3. **`tome`.** It gains `restore`, `export` and `import`. It does the host-side work: checking paths,
   ownership and archives, packing and unpacking with the system `tar`, and asking y/N. It talks to
   the updater for restore, and runs the one-shot itself for export and import.

**Tech Stack:** TypeScript, Node 22, Kysely + `pg`, `@aws-sdk/client-s3`, `yaml`, `@tiptap/markdown`,
esbuild (build only), `node:test`, Docker Compose, PostgreSQL 17 client tools (`pg_restore`, from
`postgresql-client` in the image), and GNU or busybox `tar` on the host.

**Spec:** `docs/specs/2026-10-03-tome-cli-content-design.md`. It is the binding authority, including
its planning amendments: ownership, the `verifying` phase, schema reset, categories, and the media
size limits.

**Code map:** this plan was written against the facts in the session's code map. The facts that
matter are repeated in each task's text, so no task needs the map.

## Global Constraints

- **Git:**
  - never `git stash`, in any form;
  - stage by explicit path, and commit with `git commit -F <file> -- <paths>` in its own command;
  - no attribution lines (a commit-msg hook rejects them);
  - conventional subjects that say in plain English what the owner gets;
  - never push or merge.
- **No database migration.** If a task finds it needs one, it stops and reports.
- **`UPDATER_VERSION` becomes `1.6.0`** (`src/updater/version.ts`). `/v1/status` and the update job
  record do not change in shape: apps since 1.0 parse them strictly
  (`tests/helpers/released-updater-status.ts`).
- **Paths.** Every path `tome` or the updater reads or writes resolves, by `realpath`, under
  `/var/backups/tome-cms` (`config.backupDirectory`). Everything there is owned by
  `tomecms-updater`, with mode `0600` for files and `0700` for directories. `tome`, as root,
  `chown -R`s a directory to that user before it hands it to the updater or to a one-shot. Use
  numeric ids, which you get with `stat` on `config.backupDirectory` itself.
- **One-shots** are always built from `composePrefix(config)`:
  `[...composePrefix(config), 'run', '--rm', '--name', <name>, '--no-deps', '--user', '<uid>:<gid>',
  '--env', 'DATABASE_QUERY_TIMEOUT_MS=3600000', '--volume', '<host dir>:/work', 'app', 'npm', 'run',
  '--silent', 'content', '--', <step>, ...args]`.
  - Each one-shot prints exactly one JSON line on stdout as its receipt.
  - Its stderr may carry diagnostics and is never parsed.
  - The exception is restore's migration step, which reuses the update's `npm run db:migrate`
    one-shot verbatim (`src/updater/transaction.ts:139`).
- **Commands are argv arrays**, never shell strings, everywhere.
- **Exit codes:** 0 for success, 1 for a failure or refusal, 2 for wrong usage. All three new
  commands need root and support `--help`. Output is English only.
- **Untrusted values are printed through `printable()`** (`src/cli/output.ts`). That means anything
  read from a manifest, an archive, a receipt or the database.
- **The 20 refusal sentences** in Task 4 and Task 7 are exact strings. Tests assert them.
- **Tests:**
  - **Unit:** `node --import tsx --test tests/unit/<f>.test.ts`.
  - **Integration:** `node scripts/test-foundation.mjs tests/integration/<f>.test.ts`. A new
    integration file that touches the bucket is added to `STORAGE_TESTS` in
    `scripts/test-foundation.mjs`.
  - **The integration environment** runs with `DATABASE_POOL_MAX=1` and
    `DATABASE_QUERY_TIMEOUT_MS=300`. Never read through the global `db` while a transaction is open
    on it, because it deadlocks.
  - **Operations:** `npm run test:operations:update`, plus the new restore file in Task 3.
  - **TDD:** write each test first and see it fail. Keep the RED/GREEN evidence for the report.
- **Every task ends with** `npm run check` and `npm run test:unit` green. Run
  `npm run test:operations:update` after any change under `src/updater/`.

## Review Focus

1. **A backup copied in by `rsync` as root restores.** Everything arrives root-owned, and the job
   runs as `tomecms-updater`. `tome restore` must `chown` the directory before it asks the updater.
   *Pinned in Task 4.*
2. **A backup from an older version restores into a newer one.** `pg_restore --clean` would leave
   the newer migration's tables behind, so the next `db:migrate` fails with "already exists". The
   schema must be reset first. *Pinned in Task 1, with a dump taken at migration 028 and restored
   into 029.*
3. **The updater dies or restarts mid-restore.** On boot it must put the safety backup back and
   clear maintenance, and never serve a half-restored database. *Pinned in Task 2 (unit) and Task 3
   (real containers).*
4. **A malicious or odd archive.** That covers `../`, an absolute path, a symlink, a hard link, a
   device, an oversized file, and Thai file names. The first six must be refused before anything is
   written, and Thai slugs must round trip byte for byte. *Pinned in Task 7, with Thai names also in
   Task 5.*
5. **An import that fails half-way.** For example, the 40th of 60 items has a slug that is too long.
   No item may appear, and no uploaded object or media row may be left behind. *Pinned in Task 6.*

**Interfaces:**
- `export type RestorePhase = 'verifying' | 'quiescing' | 'safety_backup' | 'restoring' | 'migrating' | 'restarting' | 'checking' | 'rolling_back' | 'succeeded' | 'failed';`
- ```ts
  export interface RestoreJob {
    id: string;
    phase: RestorePhase;
    startedAt: string;
    finishedAt: string | null;
    backupDirectory: string;
    safetyBackupDirectory: string | null;
    migrated: boolean;
    errorCode: string | null;
    report: {
      records: BackupRecordCounts;
      sealedSecrets: number;
      unopenedSecrets: Array<{ plugin: string; setting: string }>;
    } | null;
  }
  ```
- `POST /v1/restore` takes the body `{ requestId: uuid-v4, backupDirectory: string }` (exact keys)
  and answers:
  - `202 { id, phase }`;
  - `200 <record>` when the same `requestId` has finished;
  - `409 { error: 'update_in_progress' }`;
  - `409 { error: 'insufficient_disk_space' }`.

  `GET /v1/restore` answers the record, or `404 { error: 'not_found' }`.
- Error codes, which Task 4 explains to the user:
  - `backup_invalid`, `backup_other_site`, `backup_too_new` and `app_too_old` (all from
    `verifying`, with nothing stopped);
  - `safety_backup_failed` (nothing restored; the app started again);
  - `restore_failed` (rolled back to the safety backup);
  - `rollback_failed` (maintenance kept on, both paths in the record);
  - `interrupted` (from boot reconciliation);
  - `preflight_failed`.
