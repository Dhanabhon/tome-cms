# TomeCMS 1.11.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ship the Almanac theme, and Tome CLI part A (`tome status`, `logs`, `backup`, `update`,
`prune`) with updater 1.5.0, as 1.11.0.

**Architecture:**
- **Almanac** is a third theme under `src/themes/almanac/`. It uses the existing theme contract and
  shared components, with no contract or database change.
- **The CLI** is a root-only client of the updater's socket. The updater gains `/v1/backup` (with
  its own state) and `/v1/prune`, behind its existing lock. `/v1/status` and the update job record
  stay exactly as they are, because older apps parse them strictly.

**Tech Stack:** Astro 7, Node 22, TypeScript, `node:test`, Playwright, Docker Compose, Fontsource
(Trirong).

**Specs:**
- `docs/specs/2026-10-02-almanac-theme-design.md`
- `docs/specs/2026-10-02-tome-cli-server-design.md`

## Global Constraints

- **Git:**
  - never stash;
  - stage by explicit path;
  - commit with `git commit -F <file> -- <paths>` as its own command;
  - no attribution lines;
  - never push or merge.
- **No migration in 1.11.0.**
- **Almanac adds no change** to `src/themes/contract.ts` and no database change.
- **Almanac's fonts and colours:**
  - **Fonts:** Trirong (weights 400 and 600) for headings, IBM Plex Sans Thai (bundled) for body.
    Trirong is self-hosted via `scripts/sync-fonts.mjs` and loaded only on Almanac pages.
  - **Colours:** warm paper, ink and a moss-green accent, with no orange. Six panel tones: sand,
    sage, mist blue, clay pink, wheat, grey-lilac.
  - **Contrast:** at least 4.5:1 for text and links, 3:1 for graphics, in light and dark.
  - **Tokens only.** Every colour is a token in `src/themes/almanac/theme.css`.
- **Almanac's settings keys**, exactly:

  | Key | Kind |
  |---|---|
  | `hero` | switch, on |
  | `heroHeadline` | text, 120 |
  | `heroLead` | text, 240 |
  | `primaryLabel` | text, 40 |
  | `primaryLink` | text, 2048 |
  | `secondaryLabel` | text, 40 |
  | `secondaryLink` | text, 2048 |
  | `readingProgress` | switch, on |

  Labels and hints are in en and th. An empty text falls back to its default in the page's
  language.
- **Motion** is only `transform`, `opacity` and scroll timelines, and none at all under
  `prefers-reduced-motion`. Production-minified CSS must keep the longhands, tested on built CSS.
- **The updater:**
  - `UPDATER_VERSION` becomes `1.5.0`;
  - the release manifest keeps `--minimum-updater-version 1.0.0`;
  - `/v1/status` and the update `job` record keep exactly their current shape;
  - backups live in `backup-job.json`;
  - `/v1/backup`, `/v1/prune` and `/v1/apply` share one lock.
- **The CLI:**
  - root only;
  - argv arrays, never shell strings;
  - exit codes: 0 success, 1 failure or refusal, 2 usage;
  - never prints secrets (reuse the updater's redaction);
  - English output;
  - installed as `/usr/local/bin/tome`, a shim running
    `/usr/bin/node /opt/tome-cms/updater/cli/main.js "$@"`.
- **Copy and tests:**
  - every new admin or public string is in en and th, with natural Thai;
  - unit tests with `node --import tsx --test`;
  - e2e one file at a time, at most 5 `/recovery` sign-ins per file;
  - `npm run test:operations:update` for any updater, installer or upgrade change;
  - no test may depend on machine paths or the time zone.

## Review Focus

1. **A backup on a live site** must always bring the site back: the app restarts, the maintenance
   marker is cleared, `/health/ready` comes back. This holds even when the backup step fails or
   the CLI is killed mid-way, because the work runs in the updater, not the CLI. Tested in Task 5
   and the harness in Task 6.
2. **An app at 1.10.x paired with updater 1.5.0** must still read `/v1/status` during and after a
   backup or prune. Task 5 has a test against the 1.10.x client schema.
3. **`tome update` and an admin-started update must never run at once,** and neither must a
   backup and an update. Tested in Task 5 (409 from the lock) and Task 6 (the CLI's message).
4. **Almanac with real content edge cases:**
   - a post with no category;
   - a category name in Thai (the panel letter);
   - a very long title;
   - no posts at all;
   - a search with no results;
   - a site with no tagline.

   None may overflow at 390 px, and every state must render. Tested in Task 4.
5. **Switching back to Paper or Plain must look exactly as before.** Their e2e specs are re-run in
   Task 4.

### Task 5: Updater 1.5.0, `/v1/backup` and `/v1/prune`

**Files:**
- Modify:
  - `src/updater/server.ts`: the endpoints and the shared lock;
  - `src/updater/state.ts`: the backup state in `backup-job.json`;
  - `src/updater/prune.ts`: dry-run support, returning candidates with sizes;
  - `src/updater/transaction.ts`: extract the quiesce, backup and restart steps into a function
    that both an update and a backup use, without duplicating them;
  - `src/updater/version.ts`: 1.5.0.
- Test: the existing updater unit tests (grep `updater-` in tests/unit), plus a new
  `tests/unit/updater-backup.test.ts`.

Steps:
- [ ] **Tests first:**
  - **Backup:**
    - `POST /v1/backup` answers 202 with `{ id, phase }`;
    - `GET /v1/backup` follows it through quiescing, backing_up, restarting and succeeded;
    - when the backup step fails, the app is still started again and the maintenance marker
      cleared, and the backup ends failed with an `errorCode`;
    - a 409 while an update or another backup is active, and an apply is refused while a backup
      is active.
  - **Prune:**
    - with `dryRun: true`, the candidates and sizes are returned and nothing is removed;
    - with `dryRun: false`, the removed images come back in `removed`.
  - **Old apps:**
    - `/v1/status` during and after a backup still parses with the app's client schema;
    - the 1.10.x `statusSchema`, copied into the test as a fixture, also parses it.
- [ ] **Implement.** `backup-job.json` holds id, kind, phase, `startedAt`, `finishedAt`,
  `backupDirectory`, `sizeBytes` and `errorCode`. The backup writes the same public maintenance
  marker an update writes.
- [ ] **Run** `npm run test:unit` and `npm run test:operations:update`.
  Commit: `feat: the updater takes a backup or prunes images on request, one job at a time`.

### Task 6: The `tome` command

**Files:**
- Create:
  - `src/cli/main.ts`, `args.ts` and `output.ts`;
  - `src/cli/commands/{status,logs,backup,update,prune}.ts`;
  - `src/cli/socket.ts`, a small client for the updater socket, reusing types from
    `src/update/contracts.ts`.
- Modify:
  - `tsconfig.updater.json`: include `src/cli/**/*.ts`, building into `dist-updater/cli/`;
  - `scripts/updater-upgrade.ts`: install or replace `/usr/local/bin/tome` (0755, root), list it
    in the dry run, and keep the previous CLI with the previous updater;
  - `scripts/install-managed-vps.sh`: install the shim on new servers;
  - `tests/operations/managed-update.test.ts`, the harness.
- Test: `tests/unit/cli-*.test.ts`.

Steps:
- [ ] **Unit tests:**
  - parsing and `--help` for each command;
  - the root check;
  - exit codes;
  - `status` built from fixture answers, as text and as `--json`;
  - the step display from job phases;
  - the prompts and `--yes`;
  - redaction;
  - the prune dry-run table;
  - `update`: already up to date gives exit 0; a newer version prompts; and the follow loop
    covers success, rollback and `insufficient_disk_space`, which mentions `tome prune`.
- [ ] **Implement each command,** per the CLI spec:
  - **`status`:** `/v1/status`, `/health/ready` at `127.0.0.1:4321`, `docker compose ps`,
    `statfs` of the backup directory, and the newest backup in that directory.
  - **`logs`:** compose logs, or `journalctl -u tomecms-updater`, with `-n` and `-f`.
  - **`backup`:** prompt, `POST /v1/backup` with `--full`, follow `GET /v1/backup`, then print the
    path and size.
  - **`update`:** look up the newest release the way the app does (read
    `src/server/update/` for the release check and reuse it, if it runs without the app), prompt,
    `POST /v1/apply`, then follow `/v1/status`.
  - **`prune`:** a dry run by default; `--yes` removes.
- [ ] **The harness:** `tome status` and `tome prune` (the dry run) work against the harness
  server, `tome backup` succeeds and the site comes back, and `updater:upgrade` installs the shim.
- [ ] **Run** `npm run check`, the unit tests and `npm run test:operations:update`.
  Commit: `feat: tome, short commands for looking after the server`.
