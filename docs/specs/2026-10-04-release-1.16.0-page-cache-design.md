# Release 1.16.0: the public page cache

Date: 2026-10-04
Status: Design. The owner approved every section in chat on 2026-10-04. It ships as 1.16.0.

## Why

A public page today is rendered from the database on every request. Nothing caches it:
- no `Cache-Control` header is sent;
- Cloudflare in front of daedalus answers `cf-cache-status: DYNAMIC`, so it passes every request on.

On daedalus, a 1 GB VPS with a slow shared vCPU, the last measurement was 1.3.3's
(`ab -c4 -n200`, one run): the home page served 25.4 req/s and a post 36.4. The conclusion then was
that the server is CPU-bound with no hotspot left, and that the next leap would be an in-app page
cache.

**Goal:** the server takes many more readers, and does not fall over when many arrive at once.

**Success:**
- a cached home page and post serve at least 5× their current req/s, measured before and after;
- an edit is seen at once;
- the owner sets nothing up.

**Owner rulings:**
- **Freshness, C:** an edit clears the cache at once, and every entry also expires after 5 minutes
  as a backstop, for any write path that was missed.
- **Where, A:** in the app's own memory. Not Cloudflare: Cloudflare does not cache HTML without a
  rule the owner would have to add, and purging it needs an API token. TomeCMS runs as one process,
  so an in-memory cache has nothing to keep in step. A CDN layer can be its own release later.
- **`tome import`, A:** it runs as a separate process that writes the database directly. Its
  content appears within the 5-minute backstop; there is no cross-process signal.

**Not in scope:**
- Cloudflare or any CDN caching;
- a setting or an environment variable (the cap and the TTL are constants);
- caching search results;
- caching `/api/v1`, which already sends ETags;
- a migration, an updater change, or an `/api/v1` change.

## What the code says today (the facts the design rests on)

- **Readers see the same HTML.** Public HTML is the same for every reader:
  - no public page reads a cookie or `Accept-Language`;
  - the light/dark choice is made in the browser;
  - plugins are given only the page's kind and locale, and their dismissals live in the browser.
- **One exception, maintenance.** While the site is closed for maintenance, the signed-in owner
  sees the real pages (`locals.maintenanceOwner`) and everyone else sees the maintenance page.
- **Stats.** Views are counted by a browser beacon (`POST /api/v1/stats/hit`), so a cached page is
  still counted.
- **Scheduled posts.** A post goes public when its `published_at` passes (`src/server/content/live.ts`
  compares it with `now()`). Nothing is written at that moment.
- **Search.** `?q=` is rate-limited per IP (`maySearch`).
- **`/` is a 302** to the default locale.
- **Every admin write** goes through a non-GET request under `/api/admin/`, including MCP's undo
  (`/api/admin/ai-snapshots`).
- **MCP** sends every call, reads included, as `POST /mcp`. Its write tools are `create_draft` and
  `update_draft`.
- **`tome restore`** restarts the app, which empties an in-memory cache.

## 1. What is cached

**Cached:** a `GET` that answers `200`, for these bundled public paths, and only while
`TOME_CMS_FRONTEND_MODE` is `bundled`. A `HEAD` is answered from a page already kept, but never
fills the cache: a rendered `HEAD` has no body, and that empty page would be served to every `GET`
after it (ruled during implementation, commit c1841960):
- the home page, `/th` and `/en`, including a category (`?category=`) and a later page (`?cursor=`);
- a post, `/th/blog/<slug>` and `/en/blog/<slug>`;
- a page, `/th/<slug>` and `/en/<slug>`;
- `/rss.xml`, `/sitemap.xml` and `/robots.txt`.

**Never cached:**
- **requests:**
  - any request with a `q` parameter;
  - anything that is not `GET` or `HEAD`;
  - the admin, `/api/*`, `/media/*`, `/mcp`, `/oauth/*`, `/install`, `/recovery`, `/maintenance`
    and `/health/*`;
- **responses:**
  - a response that is not `200`, so a `302`, `404` or `500` is never kept;
  - a response with a `Set-Cookie` header;
- **site state:** anything while the site is closed for maintenance, or not yet installed.

**The key** is the path plus only the known parameters, `category` and `cursor`:
- they are sorted;
- `utm_source` and every other parameter are dropped, so `?utm_source=x` gets the same cached page;
- an empty value counts as absent.

## 2. How it is kept fresh

**One generation counter.** `invalidatePageCache()` empties the cache and raises the counter.

**Writes that clear it:**
- **Admin.** In `src/middleware.ts`, any non-`GET`/`HEAD` request to `/api/admin/` or below that
  answers `2xx` calls `invalidatePageCache()` after it answers. That one choke point covers every
  admin screen:
  - posts, pages, categories, navigation, slides, themes, plugins, settings, media, redirects;
  - maintenance;
  - AI undo;
  - and screens added later.

  A failed write (`4xx` or `5xx`) does not clear it.
- **MCP.** `create_draft` and `update_draft` call it after a successful write. Today they write only
  drafts, which no reader sees, but they are writers, and a later tool may publish.

**Not cleared:**
- the stats beacon, which would otherwise empty the cache on every page view;
- sign-in;
- every other public `POST`.

**Expiry.** Each entry expires at whichever comes first:
- 5 minutes after it was stored;
- the next scheduled post or page going public. This is the earliest `published_at` after `now()`
  among published posts and pages, read once when the entry is stored. A scheduled post therefore
  appears on the home page, in the feed and in the sitemap at its time.
- the next start or end of an enabled home slide (`startsAt`, `endsAt`), read the same way, so a slide
  appears and disappears on the cached home page at its time. Owner-approved ruling during
  implementation, 2026-10-05.

**The race.** A render that started before an invalidation and finishes after it must not be
stored. The generation is read when the render starts, and the entry is stored only if the
generation is unchanged when it finishes.

**`tome import`** shows within 5 minutes (owner ruling A). **`tome restore`** restarts the app, so
the cache is empty after it.

## 3. Structure

**A new module, `src/server/http/page-cache.ts`.** It is in memory, with no new dependency.
- `pageCacheKey(url: URL): string | null`: the key, or `null` when the path or its parameters are
  not cacheable.
- **A size-capped LRU** of entries, at 32 MB in total. An entry is:
  - the body bytes;
  - the response's headers, except `Set-Cookie`, `Date` and `Content-Length`, so a header a page
    sets, such as a `Link`, is kept;
  - a strong ETag (a hash of the body);
  - the expiry time;
  - the generation it was stored under.
- `lookupPage(key, now)`, `storePage(key, entry)`, `invalidatePageCache()`, and
  `pageCacheGeneration()`.
- **An entry larger than 2 MB is never stored**, so one huge page cannot flush the rest.

**In `src/middleware.ts`**, inside `answer`, before anything else for `GET` and `HEAD`:
1. **No key:** carry on as today.
2. **A fresh hit:** answer from memory at once, without reading the database, the settings or the
   session. Send the body (none for `HEAD`) with these headers:
   - the stored headers;
   - `ETag`;
   - `Cache-Control: no-cache`;
   - `X-Tome-Cache: hit`.

   If the request's `If-None-Match` matches the ETag, answer `304` with no body.
3. **A miss:**
   1. Note the generation, and render as today.
   2. If the response may be stored (`200`, no `Set-Cookie`, the site not in maintenance, bundled
      mode), read the body in full (Astro may stream it) and compute the expiry.
   3. Store the entry only if the generation is unchanged.
   4. Answer with the same body and headers, plus `ETag`, `Cache-Control: no-cache` and
      `X-Tome-Cache: miss`.

   A response that may not be stored is passed through untouched, still streaming.

**Why a hit may skip the database.** It looks as though serving a hit without reading the
maintenance setting is unsafe, but it is not:
- turning maintenance on is an admin write, so it empties the cache;
- nothing is stored while the site is closed.

So no hit can exist while the site is closed. The same reasoning covers a headless site and an
uninstalled one: neither ever stores an entry.

**HSTS.** 1.15.0's `withStrictTransport` still wraps every answer, hits and 304s included.

**The admin write hook.** It sits in `answer` around the non-GET path: when the path starts with
`/api/admin/` and the response status is `2xx`, call `invalidatePageCache()` before returning.

## 4. Testing and measurement

**Unit tests:**
- **The key:**
  - `?q=` gives `null`;
  - `utm_source` is dropped;
  - the parameter order does not matter;
  - an empty `category` counts as absent;
  - a path outside the list gives `null`.
- **The store:**
  - not `200`, or a `Set-Cookie`, is not stored;
  - past 32 MB, the least recently used entry goes first;
  - an entry over 2 MB is refused;
  - an entry expires at its time.
- **The race:** an invalidation during a render means the entry is not stored.
- **The admin hook:** a `2xx` admin `POST` clears the cache; a `4xx` admin `POST` does not; the stats
  beacon `POST` does not.
- **HEAD and 304:** a `HEAD` hit has no body; a matching `If-None-Match` gets a `304`.
- **The schedule:** the expiry is the earlier of 5 minutes, the next scheduled `published_at` and the
  next enabled home-slide start or end (integration, with the database).

**Integration and e2e tests:**
- the first request for a post says `X-Tome-Cache: miss`, and the second says `hit`;
- after the owner changes a post's title in the admin, the next request for the post shows the new
  title;
- a post scheduled a few seconds ahead appears on the cached home page once its time has passed;
- while the site is in maintenance, nothing is stored, and the signed-in owner still sees their own
  view;
- MCP `create_draft` clears the cache.

**Before and after.**
- Measure with a local production build, `ab -c4 -n200`, against the home page and a post, before
  any change and after.
- After the release, the owner runs the same on daedalus, and the numbers are compared with 1.3.3's
  (home 25.4, post 36.4 req/s).
- Target: a cached home page and post at 5× or more.

**Docs (en and th).** A paragraph in the running section. It says:
- which pages are cached;
- that an edit shows at once;
- that `tome import` shows within 5 minutes;
- how to see `X-Tome-Cache` with a `GET` that prints only the headers (`curl -s -o /dev/null -D -`).

## Release

- **Version:** 1.16.0. No migration; the updater stays at 1.6.0; `/api/v1` is unchanged.
- **Release notes:** the cache, what clears it, the 5-minute backstop, the import delay, and the
  measured numbers.
- **"For theme authors":** a theme must render the same HTML for every reader of a URL. It may
  not read cookies or request headers, because the page is cached.
