# TomeCMS 1.17.0 — signing in from a new device

Date: 2026-10-06
Status: approved by the owner as a direction ("ลุยยาว A, B, C, D ทีเดียวเลย"); details below
are rulings made under that approval, each with its reason.

## Why

On 2026-10-06 the owner could not sign in to the admin from a second computer. Three things
stood in the way, and none was a bug in one place:

1. The only passkey lived in Google Password Manager (`aaguid ea9b8d66-…`). The owner did not
   know that, the iPhone could not see it, so the cross-device QR sign-in said "no passkeys".
   Nothing in TomeCMS says where a passkey lives.
2. Adding a passkey for another device needs a passkey that works *on the device doing the
   adding* — a circle for someone whose passkey is not reachable from the new device.
3. The Turnstile challenge on the passkey sign-in refused the PC (`challenge_refused`). A passkey
   cannot be guessed or phished, and the sign-in is rate limited, so the challenge added a way
   to fail and no protection.

The owner dropped optional password sign-in (see memory, 2026-10-06). This release keeps the
admin passkey-only and makes a second device easy.

## A. Add a device with a one-time link

### Flow

1. On a device that is signed in, Security → **Add a device** → **Create a link**.
2. The screen asks for a passkey first (a recent check, as adding a spare does since 1.16.3),
   then shows a link, a QR code of the same link, a **Copy** button, when it expires, and
   **Cancel link**.
3. On the new device, open the link (scan the QR, or paste the link sent to yourself).
   `/add-device?context=…` shows "Add this device", a name field, and **Create a passkey**.
4. The browser offers whatever it can: Windows Hello (fingerprint, face or PIN), the Mac's
   Touch ID or password, Google Password Manager, a password manager, a security key, or a
   phone. TomeCMS does not restrict `authenticatorAttachment`.
5. The new passkey is added, the device is signed in, and it lands in the admin. Every other
   passkey stays.

### Rulings

| Question | Ruling | Why |
| --- | --- | --- |
| Where is a link stored? | A row in `installation_enrollments` with a new purpose, `device`. Migration `030_device_enrollment` widens the purpose check. | The install and recovery links already are exactly this: a signed, hashed, one-time context with an expiry, checked again inside better-auth's registration transaction. A second mechanism would duplicate all of it. |
| How long does a link live? | `ENROLLMENT_TTL_SECONDS`, 10 minutes, as the others. | Long enough to send a link to yourself; short enough that a leaked one is soon worthless. |
| How many at once? | One. Creating a link spends any unused device link of the owner's; **Cancel link** spends it too. | A leaked older link should stop working the moment a new one exists. |
| Who may create one? | The installed owner with a session verified in the last five minutes (`requireFreshOwnerSession`); the screen asks for a passkey first. | A link adds a credential, the most powerful thing an account can do; it gets the same bar as a spare. |
| Does it replace passkeys, as recovery does? | No. It consumes the enrollment and nothing else. | It is for adding, never for replacing. |
| Does the new device get a session? | Yes: registration with `createSession: true`, required for this purpose as it is for recovery. The session is bound to the new passkey as every session is. | Landing signed in is the point. |
| Rate limit | The `recovery` bucket (5 per 30 minutes), through the same header the recovery registration sends (`X-TomeCMS-Recovery-Context`), which now accepts `recovery` or `device`. | Unauthenticated registration with a context is the same act for both. |
| `excludeCredentials` | Kept for a device link (stripped only for install and recovery, as today). | A browser whose synced store already holds this site's passkey then refuses to make a duplicate; the page says "this device can already sign in" and links to the sign-in. |
| While a recovery is pending | A device registration fails (the session guard of migration 004 refuses the session) and the page says the link no longer works. | Recovery takes priority; nothing to add. |
| QR code | `qrcode-generator` (MIT, no dependencies), imported dynamically on the Security screen only, drawn as SVG into an `<img>`. | Scanning from the screen is the natural way to add a phone or tablet. |
| Name of the new passkey | A text field on `/add-device`, filled with a guess from the platform ("Windows device", "Mac", "iPhone", "Android device", else "New device"). | The Security list needs a name the owner recognises. |
| Audit | The new passkey appears in the Security list with its creation time and, from C, where it lives. | Enough for one owner; no new log table. |
| Reserved paths | `/add-device` joins `RESERVED_ADMIN_PATHS`, and every place that lets `/recovery` through setup, maintenance and headless mode lets `/add-device` through too. The page answers `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, as `/recovery` does. | The page must work whatever mode the site is in, and the context must not leak in a Referer. |

### Errors on `/add-device`

- No context, a bad one, an expired one or a used one: "This link has expired or was already
  used. Create a new one from a device that is signed in." with no button.
- The browser refuses because this device already holds this site's passkey
  (`InvalidStateError`): "This device can already sign in with a passkey." and a link to the
  sign-in.
- The owner cancels the browser prompt: the existing passkey error wording, button stays.

## B. Turnstile moves from the passkey sign-in to the recovery-code form

- The passkey sign-in no longer asks the sign-in plugin anything; the widget leaves the sign-in
  page.
- The recovery-code form (`/recovery`, `POST /api/recovery/start`) carries the widget and the
  server checks the token there, after the rate limit and before the code is read. A refusal is
  `403` with `code: 'challenge_refused'`; "unavailable" lets the request through and warns, as
  the sign-in did.
- The form waits for the token: pressing **Continue securely** before Turnstile has answered says
  "Wait for the check to finish" and sends nothing. After any failed attempt the widget is reset
  (`window.turnstile?.reset()`), so a spent token is never sent twice.
- A refusal logs Cloudflare's reason codes (`console.warn`, never the token), so the next
  `challenge_refused` can be read from the log.
- The plugin's description and docs say it guards the recovery-code form.

**Why here and not removed:** a recovery code is the one secret a person types; the owner who
switched the plugin on keeps a use for it. **Lockout:** when the widget cannot load, the way out
is the same as before — `npm run plugin:disable turnstile`, or `recover-owner` on the server —
and the refusal message says so.

## C. Where each passkey lives

- `src/lib/passkey-providers.ts` maps known AAGUIDs to a provider: Google Password Manager,
  iCloud Keychain, Chrome on Mac, Windows Hello, 1Password, Bitwarden, Dashlane, Samsung Pass,
  Proton Pass, KeePassXC. An unknown AAGUID whose transports include `usb` or `nfc` is a
  security key. Anything else shows no label.
- `GET /api/admin/security/passkeys` returns `provider` (a key or `null`) per passkey.
- The Security list shows the provider under the passkey's name with one line on where it can be
  used, in English and Thai. For example: "Google Password Manager — use Chrome signed in to the
  same Google account on another computer."

## D. Small fixes

- `prepare-vps.sh` run with `sudo` from a root shell: `SUDO_USER=root` is treated as no account
  (a managed install needs none), instead of refusing. An explicit `--user root` is still refused.
- The 1.16.4 release notes and the docs say to run the script without `sudo` from a root shell.

## Out of scope

- Password sign-in (dropped by the owner).
- A short typed code instead of a link.
- Notifying other devices when one is added.

## Testing

- Unit: purpose `device` in the context and enrollment schemas; provider mapping;
  `prepare-vps.sh` with `SUDO_USER=root`; the recovery form's widget behaviour where it is
  testable without a browser.
- Integration: issuing a device link spends the previous one; a device registration consumes
  the enrollment, keeps every passkey, and creates a session; an expired, used or cancelled link
  is refused; a stale session cannot create a link; the challenge applies to `/api/recovery/start`
  and not to `verify-authentication`.
- Browser: signed in on one browser context, create a link, open it in a second context with its
  own virtual authenticator, land in the admin, and see two passkeys; a used link shows the
  expired message; the sign-in page has no widget; the recovery form waits for its token.
- Operations: the managed update harness, since this release has a migration.
