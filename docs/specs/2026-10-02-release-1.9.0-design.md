# TomeCMS 1.9.0: the File Manager, pictures in the editor, plugin switches, the reading rail, and Gemini

Date: 2026-10-02
Status: Design. The owner approved the scope on 2026-10-02 and asked for spec → plan → build → release in one go.

Six items the owner asked for while testing 1.8.x. They ship together as 1.9.0. There is no migration
and no new dependency.

## 1. The File Manager: grid or list, and renaming a file

**Grid or list.**
- The File Manager gets a two-way switch, Grid (the current cards, the default) and List.
- **List** shows one row per file:
  - a small thumbnail (or the type's icon for a document);
  - the name, which is not truncated as hard as on a card;
  - the type, the size, and the dimensions for an image;
  - the date added;
  - the same actions a card has.
- The choice is remembered per browser in `localStorage`, under a try/catch; if storage is
  unavailable, the screen shows Grid.
- Both views use the same data, filters, folder chips, search and paging.
- At 390 px, List is still readable: the thumbnail and name stay, and the other details wrap under
  the name.

**Renaming.**
- Where a file's details are edited today (alt text and folder, through `saveMediaDraft`), there is
  now also **Name**. It is the file's display name, `media_items.original_name`: trimmed, 1–255
  characters, as the existing constraint requires.
- The extension is kept: if the new name drops or changes it, the server puts the original back, so
  `photo` stays `photo.webp`.
- **Nothing already placed changes.**
  - Posts and pages refer to a picture by `/media/<id>`, never by its name.
  - The stored object (`object_key`) does not move.
  - So every picture in every post keeps working, and so does the cover, the slide and the avatar.
- **A file card in a post** (an attachment) shows the name it had when the post was last saved. The
  next save of that post picks up the new name, which is what the server already does on every save.
- **Downloads keep the old file name.** A document's download name was fixed in the stored object at
  upload. Changing it would mean copying the object. The docs say this in one line.

## 2. Inserting a picture no longer jumps to the top of the post

While writing, inserting a picture (upload or File Manager) scrolls the page to the top once the
picture is in. The page should stay where the picture went.

The cause is to be found before the fix, not guessed. The likely suspects are:
- the upload dialog or picker returning focus to an element at the top of the page;
- the editor losing its selection and being re-focused at its start.

The fix keeps the scroll position, and the caret sits just after the new picture. The picture's line
is in view.

A browser test covers it. Insert a picture far down a long post, from both the upload path and the
File Manager path. The scroll position before and after must be within a small tolerance, and the
picture must be in the viewport.

## 3. Replacing a picture in the editor from the File Manager

- When a picture in a post or page is selected, a small bar beside it offers **Replace picture**
  ("เปลี่ยนรูป"). It is shaped like the table's bar (`TableBubble.tsx`).
- The bar opens the existing `MediaPicker`, limited to pictures. Choosing one swaps that picture's
  `src` to `/media/<id>` and sets its `mediaId`.
- The picture keeps:
  - its place;
  - its alignment.
- It takes the chosen file's alt text, as a fresh insert does.
- **Undo:** one Ctrl/Cmd+Z puts the old picture back.
- **The old file** stays in the File Manager.
- **The server** already accepts `/media/<uuid>` of the owner, so nothing changes there.

## 4. Confirming a plugin switch

On **Plugins**, switching a plugin on or off first asks, with the admin's own confirm dialog
(`confirmUi`). The question names the effect.

| Plugin | Switching on | Switching off |
|---|---|---|
| MCP | "AI apps you allow can read the site and write drafts." | "Every connected app stops at once. Switching it on again disconnects all of them." |
| Turnstile | "The sign-in page shows a Cloudflare check." | "The sign-in page stops showing the check." |
| Others (banner, popup, lightbox, Jev) | "{plugin} starts working on your site." | "{plugin} stops working on your site." |

Cancel leaves the switch as it was. The copy is in English and Thai.

## 5. Paper's reading rail: the current heading stands out

Today the current tick only changes colour (muted to ink), at the same 2 px and the same width, so it
is hard to see while scrolling.

From 1.9.0 the ticks look like this:

- **The current heading's tick:**
  - is **longer**: h2 about 2.5rem, h3 about 1.75rem, against 1.5rem and 1rem today;
  - is **3 px** thick;
  - uses the **accent** colour.
- **Ticks for headings already passed** are ink. Ticks still ahead stay muted.
- **The change is animated.** A tick grows from its inline-end edge with `transform: scaleX`, not
  width, so the animation stays on the compositor. Its colour changes over the theme's short duration.
- **Under `prefers-reduced-motion`**, the change is instant.

Contrast is checked in both light and dark modes. The hover label keeps working.

## 6. Gemini over MCP

The research is in `docs/research/2026-10-02-gemini-mcp.md`. The Gemini web app (custom apps) uses
OAuth with DCR. Three things in 1.8.2 stop it.

1. **The redirect.** One more allowed redirect rule:
   - `https` only;
   - host exactly `oauth-redirect.googleusercontent.com`;
   - path `/r/user_bound_custom-mcp-` followed by a non-empty id of `[A-Za-z0-9._-]`;
   - no query, fragment, userinfo or port.

   It matches by pattern, not as a fixed string, because the id is per user and per connector. A
   client's registered redirects still have to pass it, and the code still goes only to Google's
   relay.
2. **The client type.** DCR may ask for `client_secret_basic` or `client_secret_post`. Instead of
   refusing, `registerClient` registers the client as public (`none`, PKCE). The registration
   response says so, as RFC 7591 §3.2.1 allows. Anything else still refuses.
3. **The scope.** `offline_access` in an authorization request is accepted and ignored, because every
   grant already gets a refresh token. Any other unknown scope still refuses.

**The mark:** a `gemini` mark, taken from thesvg.org unmodified, is earned by that redirect. The host
is Google's own and cannot be chosen by the app. The rule stays the same: marks come only from hosts
the app cannot choose.

**The Antigravity CLI**, which replaced the Gemini CLI, uses loopback with DCR. It already works. The
docs show `agy mcp add <name> https://<site>/mcp`.

**The docs** gain "Connect Gemini". It covers the Gemini web app (Connected Apps, custom apps) and
states its limits plainly: US, 18 or over, a personal account, English. It also covers the
Antigravity CLI.

## Tests

- **Unit:**
  - the relay redirect rule, including look-alike hosts, an empty id, query, fragment and port;
  - the extension kept on rename;
  - `offline_access` ignored, and other scopes refused;
  - DCR mapping `client_secret_basic` to `none`;
  - the `gemini` brand for the relay host only;

- **Integration:**
  - a full Gemini-shaped flow (DCR with `client_secret_basic`, the relay redirect, `offline_access`,
    token);
  - rename in the media service, scoped to the owner, with a post's picture still rendering.
- **Browser:**
  - List view at 390 and 1440 px;
  - renaming;
  - the scroll position held on insert;
  - Replace picture, then undo;
  - the plugin confirm, both cancel and accept;
  - the rail's current tick, at desktop width.
