## 1. HSTS from the app

**What.** Every response the app sends carries `Strict-Transport-Security: max-age=31536000` when
`TOME_CMS_PUBLIC_URL` is `https:`. It has no `includeSubDomains` and no `preload`.

**Why the app, not Caddy** (owner's ruling, option A):
- The Caddyfile is written only when `prepare-vps.sh` runs, so a server that is already installed would
  never get the header from an update.
- The app's header reaches every managed install through the normal update.
- The media origin is not covered, but the admin's cookies live only on the CMS origin.

**Why one year from the start** (owner's ruling, option A):
- Certificates renew by themselves, through Caddy or a proxy such as Cloudflare.
- Production refuses a public URL that is not `https:` (`src/server/env.ts`).
- So a ramp, one day first and a year in a later release, would cost a release and buy almost
  nothing.

**Where.**
- A small pure function, for example `withStrictTransport(response, publicUrl)`, in
  `src/server/http/`. It returns the response with the header set.
- It sets the header only for an `https:` public URL. A dev or test stack on `http://localhost` never
  gets it, and browsers ignore the header over plain HTTP anyway.
- A response whose headers are immutable, such as a `Response.redirect` or a fetched response, is
  copied into a new `Response` before the header is set. It must never throw.
- `onRequest` in `src/middleware.ts` passes every response through it. That includes:
  - the early refusals (`crossSiteRefusal`, the install redirect, the headless 404, maintenance);
  - reads and writes alike.
- A header that is already set is left as it is, so a later per-route choice wins.

**Tests.**
- Unit:
  - the header for `https:`;
  - none for `http:`;
  - an immutable response;
  - an existing header kept;
  - the exact value, with no `includeSubDomains` and no `preload`.
- Integration or e2e: one real request to the app with an `https:` public URL carries the header.
  Use whichever stack already runs with an `https:` public URL; if none does, the unit test of
  `onRequest` with a stubbed `next` is enough.

**Docs (en and th).** Add a paragraph to `start/requirements.md` under "Two HTTPS origins":
- the CMS origin sends HSTS for a year, so a browser that has been there once always uses HTTPS;
- there is no `includeSubDomains` and no `preload`;
- the media origin does not send it;
- a proxy in front, such as Cloudflare, can add its own HSTS, which does no harm.

## 2. MCP `create_draft` honours a page's locale

**The bug.** `insertPageIn` (`src/server/content/pages.ts`) uses the site's `default_locale` for a new
page unless it is a translation or an import. MCP's `create_draft` passes `locale` with no
`sourcePageId`, so an AI that asks for a Thai page on an English site gets an English page. Posts
already do this right: `insertPostIn` uses `input.locale ?? settings.default_locale`.

**The fix.**
- A new page takes `input.locale` when it is given, else the default, as posts do.
- The admin's page API cannot send `locale` without `sourcePageId`: `createPageSchema`'s superRefine
  refuses it. So the admin's behaviour does not change.
- Correct the comment there.

**Tests** (integration, `tests/integration/mcp-tools.test.ts`):
- `create_draft` for a page with `locale: 'th'` on an `en`-default site makes a Thai page;
- the same with `locale: 'en'` on a `th` site;
- a page without `locale` still takes the default.

Write the test first and see it fail.

## 3. A saved slug keeps its address

**The bug.** Every save sends the slug back through `normalizedContentSlug`, which runs
`contentSlug`, which re-splits Thai with `Intl.Segmenter`. A slug stored as one Thai run, from an import
(`importSlug` keeps it byte for byte) or typed by hand, comes back split, as in `สวัสดีครับ` →
`สวัสดี-ครับ`. So the address changes on an edit the writer never made to it.

Published items leave a `content_redirects` row, so old links still arrive. Drafts and the writer's
expectations do not survive it, though.

**The fix** is in one place, `normalizedContentSlug` in `src/server/content/mutations.ts`, which
every create and update path uses (posts create and update, pages through `pageSlug`, duplicates):
- A requested slug that, after `normalize('NFC').trim()`, already matches `SLUG` and fits
  `SLUG_LENGTH` is returned as it is.
- Anything else goes through `contentSlug` as today, and an empty request still falls back to the
  title, then to `post-<id>` or `page-<id>`.
- `pageSlug`'s reserved-slug check still runs on the result.
- `importSlug` can then call the shared rule instead of repeating it, if that is a smaller diff. Its
  reserved-page check stays.

The admin editor derives a slug from the title only while the slug is untouched, and never for an
existing item (`slugTouched` starts true), so nothing changes client-side.

**Tests.**
- Unit:
  - a valid Thai run comes back unchanged;
  - a valid Latin slug comes back unchanged;
  - a messy one (`Hello World!`, mixed case, spaces) is still normalised;
  - an empty one falls back to the title, then to the id;
  - one over `SLUG_LENGTH` is cut by `contentSlug` as today.
- Integration: update a post whose stored slug is one Thai run without changing the slug; the slug
  and address stay. Do the same for a page.

## 4. Plain

**a. Heading sizes in a post or page body** (`.plain-body`):
- `h2` goes from `--text-xl` (22 px) to **28 px**;
- `h3` goes from `--text-md` (20 px) to **22 px** (`--text-xl`);
- margins, weight and line height stay;
- 28 px has no core token, so add one to Plain's own token block (for example
  `--plain-text-h2: 1.75rem`), never a raw value in the rule;
- Thai leading stays at 1.2 or more.

**b. The article title** (`.plain-article h1`): `text-wrap: balance` becomes `pretty`, so the title
fills its line before it wraps. It is the same fix 1.14.1 made to the home lead. The grid card titles
stay `balance`: they are narrow, and balancing is right there.

**c. The ©.** Google Sans draws © small and raised, like a superscript. It affects Plain and Paper,
which both set their footers in Google Sans; Almanac's face draws it at full size.
- In Plain's `Shell.astro` and Paper's `parts/Footer.astro`, wrap the `&copy;` in a span with a class
  (for example `.copyright-mark`).
- Give that class a system font family token, so only that one character changes face.
- The rest of the footer stays Google Sans.
- Almanac is unchanged.

**Tests.** Unit (CSS parsing, as the theme tests do):
- the h2 and h3 sizes;
- `pretty` on `.plain-article h1`;
- the copyright span exists in both themes' footers and its class names a system family.

## 5. Paper: the covers slider below 64rem

**The problem.** With hero set to "Covers of the newest posts" (`hero: 'slider'`), the title sits
over the picture on its scrim, and the three buttons sit over the picture's bottom end. Below 64rem a
long title runs under the buttons. The "Your slides" hero already moves its buttons below the words
there; the covers slider does not.

**The fix** (owner's ruling: room on the right):
- Below 64rem, the covers slider's caption reserves space at its inline end for the buttons: three
  2.75rem buttons, their gaps and the edge inset. A long title then wraps before it reaches them.
- On a phone (below 37.5rem), that reservation would leave the title under half the slide's width.
  There, the caption instead reserves the buttons' height below the words, so the title sits above
  them.
- Either way the title is never under a button.
- 64rem and up is unchanged.
- Tokens only. The 2.75rem is the buttons' own size; name it once if it is repeated.

**Tests.**
- Unit: the caption's reservation rules exist below 64rem.
- Shots: theme-shots gains a `home-covers` screen for Paper, with hero set to `slider` and a long
  cover title, at all five widths.

## 6. Touch targets under a coarse pointer

**The rule** (from 1.14.0, never measured): under `@media (pointer: coarse)`, every control is at
least **44 × 44 CSS px**. This covers:
- buttons;
- icon buttons;
- menu and nav links;
- pills and chips;
- switches, selects and inputs;
- pagination;
- the language and scheme switches;
- the slider buttons;
- footer links.

**Exempt** (WCAG 2.5.8's own exceptions):
- links inside running text (`.post-body`, `.plain-body`, Almanac's body, an excerpt);
- a control the browser draws with no author styling.

**How it is found.** A new e2e spec, `tests/e2e/touch-targets.spec.ts`:
- **Device:** a coarse-pointer context (`hasTouch: true`, `isMobile: true`, width 375). It first
  asserts `matchMedia('(pointer: coarse)').matches`.
- **Themes:** for each of the three themes, it visits home, post, category, search and 404.
- **Admin:** it visits the screens `admin-shots.spec.ts` covers. It signs in once: at most 5
  `/recovery` sign-ins per spec file.
- **Measurement:** every visible `a, button, [role=button], input, select, summary, [tabindex="0"]`
  outside the exempt containers. A target fails when its border box is under 44 in either direction.
- **Output:** the failures, listed by screen, selector and size.

This spec is a CI gate, so it must pass on the release. Seed it the way `theme-shots.spec.ts` does,
without signing in, for the themes.

**How the small ones grow.**
- Under `@media (pointer: coarse)` only. A mouse user sees no change.
- Prefer `min-block-size` and `min-inline-size` with the content centred, using an existing
  field-height or 44px token if there is one; add one if not.
- Where growing the box would break a layout, such as a dense inline footer, the spacing between
  targets may carry it instead. Each such case is named in the plan's ledger with the reason, and
  the spec's check allows exactly those selectors.

**First step.** Run the spec once before fixing anything, and record the failure list in the plan's
ledger. That list, not a guess, is the work.
