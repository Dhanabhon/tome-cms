# TomeCMS 1.21.0 — loose ends after 1.20.0

Date: 2026-10-07
Status: approved by the owner ("1 - 8 มัดรวมกันเลยได้ไหม แล้วออกเวอร์ชันใหม่ ผมอยากสั่งทีเดียวจบ"),
including releasing it when done. The eight items are the list the controller gave after 1.20.0;
the rulings below are the controller's.

## 1. A browser test of the real installer

No test runs `POST /api/install/finalize` for real: `passkey-installer.spec.ts` mocks it and
`tests/operations/fresh-install.test.ts` only checks that destructive operations need explicit
targets. Add one test that installs a site on an empty database through the real route (virtual
authenticator, real passkey registration, real finalize) and then checks what finalize wrote: the
owner, the site settings, the default category (`Uncategorized`, slug `uncategorized`), the
recovery codes shown once, and that the admin opens. It runs in CI with the other tests.

## 2. Sweeping objects nothing points at

A crash between an object's upload and its row, a failed best-effort delete, or a 1.19.x rollback
deleting images leaves objects in the bucket that no row tracks; `reset --execute` then refuses the
bucket. Add a sweep:

| Question | Ruling |
| --- | --- |
| What | Objects under the TomeCMS key grammar (`isTomeObjectKey`) that no row tracks: not a media item's original, not a variant, not a brand image, not a pending upload reservation. The "tracked" list is the one reset already builds (`knownObjects`) — one source of truth. |
| Age | Only objects older than 24 hours, so an upload in flight is never touched. |
| How | `npm run media:cleanup -- --orphans` lists them (dry run); `--orphans --execute` deletes them. On a managed install, `sudo tome prune` runs the dry run and says how to delete; `sudo tome prune --orphans` deletes. |
| Never | Objects outside the key grammar (another app's), objects younger than 24 h, anything a row points at. |
| Reset | When `reset --execute` refuses because of untracked TomeCMS objects, its message names the sweep. |

## 3. Docs: the device-link limit

The recovery page (en + th) says creating a device link is limited to 10 in 15 minutes, as it
already says for recovery and install.

## 4. Paper's covers slider on narrow screens

Below 37.5rem the slider crops 16:9 covers into a 4:3 box, so a cover is drawn about 133 % of the
viewport wide. Its `sizes` says `100vw`; make it say what is drawn (`(max-width: 37.5rem) 134vw,
100vw`, derived from the CSS, pinned by the drift test).

## 5. `tome import` that fails part-way

If the import fails after pictures were queued, the clients close while the jobs wait and each logs
"Image variants could not be made." Wait for the queue in `finally` too (errors from the wait are
logged once, never hide the import's own error).

## 6. Renaming "Uncategorized"

The default category's name can be changed (e.g. "ไม่มีหมวดหมู่"); its slug stays `uncategorized`,
it stays the default, it still cannot be deleted, and it still has no page. Descriptions stay
hidden for it (no page shows them). One migration, `034_default_category_name`, relaxes the
migration-005 trigger to allow a name change only. Nothing in the code may find the default
category by the literal name "Uncategorized"; it is found by `is_default`.

## 7. Malformed percent-escapes

Ruling: no change. `@astrojs/node` standalone answers `400 Bad request.` before the app for a URL
`decodeURI` rejects; that is the correct status, it is never cached, and a themed 404 would mean
replacing the server entry (Dockerfile `CMD`, installer, updater). Only the dev server answers 500,
which no visitor sees.

## 8. The editor-blocks flake

`tests/e2e/editor-blocks.spec.ts` "a line and a table cell can be aligned, from either bar" fails
under full-suite load and passes alone. Find the race and fix it in the test (deterministic waits),
or in the editor if the race is real for users.

## 9. A "Tome CLI" section in the documentation

Added by the owner on 2026-10-07 ("อัปเดตคู่มือ เพิ่มเมนูเกี่ยวกับการใช้งาน Tome CLI ด้วยนะ release ไปพร้อมกันเลยกับ 1.21.0").
Today `tome` is one 432-line page, `running/cli.md`, under "Running a site". Give it a sidebar
section of its own, "Tome CLI" (th: "Tome CLI"), placed after "Running a site", with one page per job,
in English and Thai:

| Page | Covers |
| --- | --- |
| Overview | What `tome` is, where it runs (a managed server, `sudo`) and where it does not (a source checkout uses `npm run tome --`), installing it, the rules every command follows, and a table of all commands with links. |
| Status and logs | `tome status`, `tome logs`. |
| Backups and restore | `tome backup`, `tome restore`. |
| Updates and clean-up | `tome update`, `tome prune` (incl. `--orphans` from §2), when the disk is full. |
| Moving your writing | `tome export`, `tome import`. |
| Themes and plugins | the checkout commands: `theme new`, `plugin new`, `check`. |

Every command's text keeps what today's page says (no behaviour invented); examples stay
copy-pasteable. The old address `/running/cli/` redirects to the new overview, and every link in
the docs to `running/cli` (with its anchors) points at the new page that now holds that part.
