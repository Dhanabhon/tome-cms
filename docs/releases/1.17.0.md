# TomeCMS 1.17.0

Date: 2026-10-06
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.17.0 makes it easy to sign in to the admin from a second device. A signed-in device
makes a one-time link; the new device opens it and gets a passkey of its own. The Security
screen now says where each passkey lives, and the Turnstile check moves from the passkey sign-in,
where it could only get in the way, to the recovery-code form. `/api/v1` is unchanged.

## Upgrading

- **A managed install** updates from "System" in the admin, as
  [Updating](https://dhanabhon.github.io/tome-cms/running/updating/) describes, or with
  `sudo tome update` on the server. This release has one migration, `030_device_enrollment`, so
  the updater takes a full backup (database and media) before it applies it.
- **A build from source** upgrades in place by running the deploy helper again; it runs the
  migration.
- **The updater** stays at 1.6.0. Nothing to upgrade on the server.
- **Turnstile:** if the Cloudflare Turnstile plugin is on, the admin sign-in no longer shows it.
  The recovery-code form does instead.

`deploy/cloud-init.yaml` now installs 1.17.0.

## Added

- **Add a device.** Security → Add a device → Create a link. The screen asks for a passkey,
  then shows a link and a QR code of it, which work once, for 10 minutes. Open the link on the
  new computer, phone or tablet (scan the QR code, or send the link to yourself) and press
  "Create a passkey". The device keeps a passkey of its own and is signed in; every other passkey
  stays. It does not matter where your first passkey lives, and the new device needs no phone or
  Bluetooth. A device without a fingerprint reader asks for its PIN or password instead.
  - Making a new link, pressing "Cancel link", using the link, or starting an account recovery
    ends the previous link.
  - A link that is used, cancelled or expired says so when it is opened, and offers nothing to
    press. A device that already holds this site's passkey is told it can sign in already.
- **Where each passkey lives.** Under each passkey the Security screen names its home when it
  can tell — Google Password Manager, iCloud Keychain, Chrome on a Mac, Windows Hello,
  1Password, Bitwarden, Dashlane, Samsung Pass, Proton Pass, KeePassXC, or a security key — and
  says where else it can be used.

## Changed

- **The Turnstile plugin guards the recovery-code form, not the passkey sign-in.** A passkey
  cannot be guessed or phished, and the sign-in is rate limited, so the check added only a way to
  fail: an owner on a second computer was refused although the passkey worked. A recovery code is
  the one secret a person types, so the check stands there. The form now waits for the check to
  answer before it sends anything, asks for a fresh check after every failed attempt, and, when a
  check is refused, the server logs Cloudflare's reason codes. If the check never appears, the
  message names the way out: `npm run plugin:disable turnstile` on the server.

## Fixed

- **`prepare-vps.sh` under `sudo` from a root shell.** It took `root` for the account a build
  from source needs and refused to run. A managed install needs no account, and the script now
  runs either way. An explicit `--user root` is still refused.

## Security

- Creating a device link needs an owner session verified in the last five minutes, as adding,
  renaming and deleting a passkey do.
- A link is signed, stored only as a hash, and checked again inside the registration
  transaction, which consumes it together with creating the passkey and the session, so it
  cannot be used twice. A link never removes a passkey or a session.
- `/add-device` accepts only a device link; an install or recovery link opened there is refused.
  The page is never cached and sends no referrer.

## Testing

- **Unit:** the `device` purpose in signed contexts; the device-name guess; `/add-device` as a
  reserved admin path and through setup, headless and maintenance; the passkey provider map,
  including keys with no AAGUID; the recovery form's wait-and-reset copy; `prepare-vps.sh` with
  `SUDO_USER=root`.
- **Integration:**
  - the migration widens the purpose check, and a device enrollment is valid only for the
    installed owner;
  - issuing a link ends the previous one, cancelling ends the current one, a recovery ends it, a
    stale session cannot make one;
  - a device registration consumes the link, keeps every passkey and session, and cannot be
    repeated;
  - the recovery-code start is refused without a Turnstile token, logs the reason and never the
    token, and the passkey sign-in is never refused for a missing one.
- **Browser:**
  - a signed-in owner with a ten-minute-old session makes a link; a second browser with its own
    authenticator opens it, creates a passkey and lands in the admin; the first screen then says
    the device was added;
  - a used link, a cancelled link and a recovery link opened at `/add-device` show the expired
    message on load; a device that already holds the passkey is told so;
  - the recovery form waits for Turnstile's token, sends it once, and resets the check after a
    refusal.
- **By hand:** the QR code decodes when drawn at its size on a 1x screen.
