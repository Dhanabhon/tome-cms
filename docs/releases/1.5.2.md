# TomeCMS 1.5.2

Date: 2026-09-30
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.5.2 fixes uploads that fail at "Storage verification is temporarily unavailable. Try
finalizing again." on a site whose media address sits behind a CDN such as Cloudflare. `/api/v1` is
unchanged.

## Upgrading

- **A managed install** updates from "System" in the admin, as
  [Updating](https://dhanabhon.github.io/tome-cms/running/updating/) describes. There is no
  migration, no new setting and no new runtime dependency, so the updater backs up the database alone.
  Nothing needs changing on the server: the application finds the bundled storage by itself.
- **A build from source** upgrades in place by running the deploy helper again. If its storage sits
  behind a CDN, set `S3_INTERNAL_ENDPOINT` (below) to an address the host reaches directly.

`deploy/cloud-init.yaml` now installs 1.5.2.

## Uploads behind a CDN

An upload has two halves. The browser sends the file to storage through the public media address
(`S3_ENDPOINT`), and the application then checks what arrived: its size, its checksum and, for a
document, its contents. Until now the application made those checks through the same public address.
With a CDN in front of it, each check went out to the CDN and back, and the CDN does not pass every
signed request on unchanged: for a file it has not cached yet (a PDF is a type it caches), storage saw a
different request from the one that was signed and refused it, and the owner saw "Storage verification
is temporarily unavailable". An image usually got through, because its check sends a plainer request.

From 1.5.2 the application reaches storage on an address of its own:

- `S3_INTERNAL_ENDPOINT` when it is set;
- on a managed install without it, the bundled SeaweedFS at `http://seaweedfs:8333`, on the same Docker
  network — so a managed install needs no change, and a new one also sets it in its Compose file;
- otherwise `S3_ENDPOINT`, as before.

The upload links the browser uses are still signed for `S3_ENDPOINT`, and readers still load media from
`MEDIA_PUBLIC_URL`; a CDN can stay in front of both. `http:` is accepted for the internal address, which
never leaves the machine or the private network.

On a build from source, the backup, media cleanup and reset scripts read `.env.local` on the host, so an
internal address there must be one the host can reach, such as `http://127.0.0.1:9000`.

The backup the updater takes while installing 1.5.2 still runs in the version being replaced, so it
reads the bucket through the public address one last time; a plain read passes a CDN, as it did for
every earlier update.

## The admin

On Themes, the theme in use keeps "Customize" beside "View site" at the end of its row, with "In use"
alone at the start.

## Testing

- `tests/unit/storage-endpoints.test.ts` covers the three ways the address is chosen, the `http:`
  internal address in production, and that an upload link carries the public host while the
  application's own requests go to the internal one; a source check keeps the public client to
  presigning alone.
- Before release, the checks a finalize makes (a head with its checksum, a read pinned to the head's
  ETag, a range read) were run against SeaweedFS 4.46 at `http://seaweedfs:8333` from inside a Compose
  network.
