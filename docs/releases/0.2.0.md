# TomeCMS 0.2.0

Date: 2026-09-13
Status: Release candidate; not tagged for production

TomeCMS 0.2.0 replaces the original provider-coupled backend with a headless-capable core built on PostgreSQL, Better Auth, and S3-compatible object storage. This is a pre-1.0 clean-install release.

## Breaking changes

- A clean installation is required. There is no automated import, dual-write path, or compatibility layer for existing Supabase users, sessions, rows, or objects.
- Supabase runtime packages, environment variables, SQL assets, and import paths have been removed.
- Authentication is Passkey-first. Production registration and sign-in require a valid HTTPS origin; loopback HTTP remains supported for local development.
- Deployments must provide the PostgreSQL, authentication, recovery, public-origin, and S3 values documented in `.env.example`. Permanent object-storage credentials remain server-only.

## Highlights

- PostgreSQL 17 with Kysely migrations owns authentication, settings, Posts, Pages, shared Categories, Navigation, previews, and File Manager metadata.
- Better Auth provides database-backed sessions, Passkeys, one-time recovery codes, and local owner recovery.
- Media uploads use short-lived signed S3 requests, server-side verification, stable media identities, and retry-safe cleanup.
- The read-only `/api/v1/content` REST API publishes Site Settings, Posts, Pages, Categories, and Navigation with explicit DTOs, signed cursors, CORS, ETags, caching, and an OpenAPI 3.1 document.
- Draft previews use short-lived scoped tokens and private responses.
- `TOME_CMS_FRONTEND_MODE=bundled` serves the zero-application-JavaScript Astro Blog; `headless` keeps Admin and APIs while hiding the bundled public routes.
- Sitemap, RSS, and robots endpoints follow the selected frontend mode.

## Operations

- `npm run dev:macos` is the primary local bootstrap; the Windows helper is functionally equivalent but remains the secondary path.
- The Linux VPS helper starts PostgreSQL and SeaweedFS, creates the media bucket, builds the application image, runs migrations once, and waits for `/health/ready` without requiring a storage license.
- `npm run backup` writes the PostgreSQL custom dump, S3 object mirror, and checksum manifest as one offline recovery point. A database-only backup is incomplete.
- `npm run restore:check` restores only into an explicitly named disposable Compose project and removes its volumes afterward.
- `npm run admin:reset-installation` defaults to a preview. Its execute mode retains the schema, migration history, environment file, and installation token so the next start returns to the Wizard.

## Validation boundary

`npm run check` and `npm run build` pass for this candidate. Focused operation, bootstrap, liveness, and configuration checks also pass.

Before tagging or deploying 0.2.0 to production, complete the full integration and browser acceptance matrix, verify backup/restore and reset/reinstall against disposable services, and test Passkey registration/sign-in through a real HTTPS VPS hostname.

The 2026-09-13 production dependency audit is also a release blocker: the installed Astro 5 line has unresolved critical advisories and its bundled Sharp version has unresolved high advisories. The registry offers remediation only through a major Astro/adapter upgrade, which needs a separate compatibility pass rather than an unsafe automatic fix. Tiptap 2 also has a moderate advisory whose patched release is in Tiptap 3. Do not tag this candidate until those upgrades are completed and the audit is rerun.
