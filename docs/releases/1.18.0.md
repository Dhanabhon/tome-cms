# TomeCMS 1.18.0

Date: 2026-10-06
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.18.0 adds a switch that keeps a site out of search results. `/api/v1` is unchanged.

## Upgrading

- **A managed install** updates from "System" in the admin, as
  [Updating](https://dhanabhon.github.io/tome-cms/running/updating/) describes, or with
  `sudo tome update` on the server. This release has one migration, `031_search_visibility`, so
  the updater takes a full backup (database and media) before it applies it. An install on 1.16.4
  or older also gets 1.17.0's `030_device_enrollment` on the way.
- **A build from source** upgrades in place by running the deploy helper again; it runs the
  migration.
- **The updater** stays at 1.6.0. Nothing to upgrade on the server.
- The switch starts off, so nothing about a site changes until its owner turns it on.

`deploy/cloud-init.yaml` now installs 1.18.0.

## Added

- **Search results.** Settings has a new part, "Search results", with one switch: "Keep this
  site out of search results". Turned on and saved:
  - every public page carries `<meta name="robots" content="noindex, nofollow">`;
  - every answer the site serves to readers and to the content API carries
    `X-Robots-Tag: noindex, nofollow`, the feed and the sitemap included;
  - the sitemap lists nothing, and `robots.txt` no longer points to it;
  - the admin's sidebar says "Hidden from search" under the site name, linking back to the
    switch, so it is not left on by mistake.

  It asks rather than blocks. `robots.txt` still lets crawlers in, because a page they may not
  fetch is a page whose `noindex` they never read, and a site that is already listed would stay
  listed. Search engines and AI crawlers that follow the request drop the pages; nothing stops a
  person from visiting. Files served from the media host do not carry the request. To close the
  site, use Maintenance.

  Turned off (the default), every page, header, feed, sitemap and `robots.txt` is exactly as
  before. In headless mode the switch reaches the content API only; the frontend you build asks
  crawlers itself.

## Testing

- **Unit:** `robots.txt` listed, hidden and headless; an empty sitemap is still a valid one; the
  header on every public answer when the switch is on, on none when it is off, and never on the
  admin, its API, install, recovery or health; a page cached before the switch is not served after
  it; the wording in both languages; the setting never appears in `/api/v1`.
- **Integration:** the switch is saved and read back, and a fresh install starts with it off.
- **Browser:** turning the switch on in Settings shows the sidebar mark and puts the meta and the
  header on the site, its feed, its sitemap and the content API, takes the sitemap line out of
  `robots.txt`, and turning it off puts everything back; the sidebar mark is a 44-pixel target on a
  touch screen.
- **Operations:** the managed update harness, with the migration.
