# TomeCMS 1.13.0

Date: 2026-10-03
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.13.0 can put a backup back into the site and move a site to a new server, and it can
keep a readable Markdown copy of everything you have written. All of it runs on the server, with
`sudo tome`; nothing new is open to the outside. `/api/v1` is unchanged.

## Upgrading

- **A managed install** updates from "System" in the admin, as
  [Updating](https://dhanabhon.github.io/tome-cms/running/updating/) describes, or with
  `sudo tome update` on the server. There is no migration, so the updater backs up the database
  alone.
- **The updater** goes to 1.6.0. `tome restore`, `tome export` and `tome import` exist only after
  you upgrade it, once, from a checkout of this release:
  ```bash
  cd /opt/tome-cms-src
  git fetch --depth 1 origin tag v1.13.0
  git checkout --detach v1.13.0
  npm ci
  sudo npm run updater:upgrade -- --dry-run
  sudo npm run updater:upgrade
  ```
  Update the application to 1.13.0 first, then upgrade the updater.
  Until then the site runs 1.13.0 normally, and the old `tome` has no such commands.
- **A build from source** upgrades in place by running the deploy helper again.

`deploy/cloud-init.yaml` now installs 1.13.0.

## Restoring a backup: `sudo tome restore <backup>`

- **What it does.** It puts a backup made by `tome backup` (or by the updater before an update)
  back into the site. That is the database, and for a full backup the media too. A backup from an
  older version is migrated forward.
- **Before the question.** It checks the backup and shows what it holds. It refuses one from
  another domain, from a newer version, or one that is damaged.
- **During the restore.** It first takes a safety backup of the site as it is now. The site is in
  maintenance while it works, and everyone is signed out at the end. MCP connections are kept.
- **If anything fails,** the safety backup is put back.
- **After a move to a new server,** it lists any plugin secrets to set again, and says to issue new
  recovery codes.

[Backups and restore](https://dhanabhon.github.io/tome-cms/running/backups/) describes moving to a new
server step by step, and [Recovery](https://dhanabhon.github.io/tome-cms/running/recovery/) covers the
rare case where putting the safety backup back fails too.

## A Markdown copy: `sudo tome export` and `sudo tome import <archive>`

- **`export`** writes every post and page, in every language and status, to
  `/var/backups/tome-cms/markdown-<time>.tar.gz`:
  - a readable `.md` for each, with front matter;
  - an exact `.tome.json` beside it;
  - every image and file they use.

  The site stays up while it runs.
- **`import`:**
  - **Before anything is written,** it shows what it will create and what it will skip. A post
    whose address is already taken is skipped, never overwritten. `--dry-run` stops there.
  - **Every post keeps** its status, its dates and its address, Thai addresses included.
  - **It is all or nothing:** everything comes in, or nothing does.
  - **It refuses an archive** that holds a link, a path outside itself, or anything its own listing
    hides.

## Testing

- **Unit tests** cover:
  - every refusal;
  - the archive checks, run against both bsdtar and GNU tar with crafted archives;
  - the front matter;
  - the import plan.
- **Integration tests:** a site exported and imported into an empty one comes back equal. A failed
  import leaves nothing behind. A backup from an older schema restores and migrates.
- **A new operations harness** runs a restore, its fallback to the safety backup, and an updater
  restart in the middle of a restore, all against real PostgreSQL and SeaweedFS. CI runs it.
- **The real application image** was smoke-tested on its own one-shots:
  - a 1.12.1 backup restored into 1.13.0;
  - an export;
  - an import into a fresh database, with Thai addresses kept byte for byte.
