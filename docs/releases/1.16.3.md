# TomeCMS 1.16.3

Date: 2026-10-05
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.16.3 fixes what a security scan of the whole repository found. None of it was rated
critical or high, and each fix was checked by an independent reviewer before it landed.
`/api/v1` is unchanged.

## Upgrading

- **A managed install** updates from "System" in the admin, as
  [Updating](https://dhanabhon.github.io/tome-cms/running/updating/) describes, or with
  `sudo tome update` on the server. There is no migration, so the updater backs up the database
  alone.
- **A build from source** upgrades in place by running the deploy helper again.
- **The updater** stays at 1.6.0. Nothing to upgrade on the server.

`deploy/cloud-init.yaml` now installs 1.16.3.

## Security

- **A spare passkey needs a recent check.** Updates, new recovery codes and MCP consent already
  asked the owner to confirm with a passkey within the last five minutes. Adding a spare passkey
  did not, and registering one also signed the owner in again with a fresh session. So anyone
  holding an old owner session, for example a cookie left on a shared computer, could add a
  passkey of their own and use the fresh session to pass those other checks. The server now
  refuses a spare from a session older than five minutes, and the Security screen asks for a
  passkey before adding one. Installing and recovering are unchanged.
- **MCP Markdown is trimmed in one pass.** Trimming the text around a picture used a pattern that
  slowed down with the square of the length of a run of spaces or tabs, on the server's main
  thread, outside the Markdown worker's time limit. A draft sent through MCP with a few hundred
  thousand tabs before a picture could hold every page of the site for over a minute. It now uses
  the built-in trims, which remove exactly the same characters.
- **A brand SVG that hides markup in its style is refused.** The SVG sanitizer keeps `<style>`
  and writes its text out as it is. Markup written as entities (`&lt;script&gt;`) or inside CDATA
  was decoded first, so it came out as live tags in the stored logo or icon, which run when the
  file is opened at its own address. Such a file is now refused with "brand_svg_unusable".
  Ordinary SVGs from drawing programs are accepted as before.

## Testing

- **Unit:**
  - a spare passkey from a stale session, or a session with no valid date, is refused, and one
    from a fresh session is taken;
  - 200,000 tabs before a picture are trimmed within the test's five-second bound (about a quarter of a second);
  - a brand SVG with entity-encoded or CDATA markup in its style is refused.
- **Browser:** an owner whose session is ten minutes old adds a spare passkey on a second device
  after confirming with the first. Without the Security screen's check, the test fails.
