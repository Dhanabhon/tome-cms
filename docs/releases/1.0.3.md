# TomeCMS 1.0.3

Date: 2026-09-28
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.0.3 makes an update from the admin stop the application in time, and go back cleanly
when it cannot. A job that failed before its backup can now be cleared with one command. The
"System" screen shows an update's progress in the owner's language, and puts it away once it is
done. The project also gains a Code of Conduct.

## Upgrading

- **A managed install from 1.0.1 or 1.0.2: add an init first.** Before you update from the
  admin, run as root:

  ```sh
  grep -q '^    init: true' /opt/tome-cms/compose.managed.yaml || sed -i '/^  app:$/a\    init: true' /opt/tome-cms/compose.managed.yaml
  cd /opt/tome-cms && docker compose -p tomecms -f compose.managed.yaml \
    --env-file /etc/tome-cms/tome-cms.env \
    --env-file /var/lib/tome-cms/updater/image.env up -d --wait --no-deps --pull never app
  ```

  A web update replaces only the application image. The Compose file and the updater stay as
  the server was installed, so without this step the update stops at "Prepare maintenance", as
  it did on the first real one. Then update from "System", as
  [Updating](https://dhanabhon.github.io/tome-cms/running/updating/) describes. There is no
  migration, no new setting and no new runtime dependency.
- **A managed install from 1.0.3 on** already runs the application under an init.
- **A build from source** upgrades in place by running the deploy helper again.

`deploy/cloud-init.yaml` now installs 1.0.3.

## Updating from the admin

The first update from the admin on a real server, 1.0.1 to 1.0.2, stopped at "Prepare
maintenance" and left the site down:

- **The application ignored the signal to stop.** It is Node running as the container's first
  process, which ignores `SIGTERM`, so `docker compose stop` waited out its whole 30 seconds and
  then killed it. `compose.managed.yaml` now runs it under an init, which passes the signal on:
  on the 1.0.1 image, stopping took 15 seconds and ended with exit code 137 without it, and 1
  second with it.
- **The updater gave that stop exactly its grace period.** The command now has the 30 seconds
  plus 30 more for Docker itself.
- **The rollback started the application while Docker was still stopping it.** It now stops it
  again first, then starts the previous version.

The last two are in the updater, which a web update does not replace. They reach a server
installed with 1.0.3 or later; the init above covers a 1.0.1 or 1.0.2 one.

## Clearing a failed update

An update that ends in `failed_manual_recovery` blocks every later one. When it stopped before
its backup, nothing changed: the backup is recorded before any migration or switch of image. For
that case, `sudo npm run updater:clear-failed`, run from a checkout of the release, stops the
updater, moves the job aside as `job.json.cleared-<id>`, and starts the updater again. It refuses
a job that recorded a backup, and one whose installed image is no longer the previous one.
[Troubleshooting](https://dhanabhon.github.io/tome-cms/running/troubleshooting/) walks through it.

## The admin

- The progress line was the updater's English message, such as "Update installed
  successfully." on the Thai screen. It is now worded from the update's step, in English or
  Thai.
- The backup time followed the browser's format, such as "9/28/2026, 3:22:24 PM." It now
  follows the admin's language, with the Buddhist year in Thai.
- The step-by-step card stayed on "System" for good after an update. It now shows while an
  update runs, or while you watch one finish. Otherwise a "Last update" card gives the result,
  the version, when it finished, and the backup time.

## The documentation and the project

- Troubleshooting gains an "Updating" section: the update that stops at "Prepare maintenance",
  and the message the clearing command gives for a job it will not clear. Updating warns
  servers installed with 1.0.1 or 1.0.2 about the init. English and Thai.
- `CODE_OF_CONDUCT.md` is the Contributor Covenant 2.1. Reports go privately to the maintainer,
  through the contact details on their GitHub profile.

## For theme authors, plugin authors and headless sites

Nothing a theme, plugin or headless site depends on changed.

## Validation boundary

- `npm run check` passes, and the documentation site's check and build pass.
- `npm run test:unit`: 599 tests, all passing, among them: the stop command's time, a stop that
  times out and rolls back after a second stop, `init: true` in `compose.managed.yaml`, clearing
  a job only when it stopped before its backup, and the progress wording, backup time and card
  visibility in both languages.
- `npm run test:operations:update`: 9 of 9 passing.
- On the DigitalOcean server (`linux/amd64`), the 1.0.1 to 1.0.2 update failed as described,
  the site came back on 1.0.1 after `init: true` was added by hand, the failed job was set aside,
  and the same update then succeeded from the admin, with a recovery backup, and an upload
  worked on 1.0.2. The new updater code has not yet run on a real server: that server keeps the
  updater it was installed with, from 1.0.1. A fresh 1.0.3 install is its first run.
