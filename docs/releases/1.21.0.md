# TomeCMS 1.21.0

Date: 2026-10-07
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.21.0 closes the loose ends left after 1.20.0: the default category can be renamed,
`tome prune` finds media files nothing points at, the installer is tested end to end, and the
`tome` command has a section of its own in the documentation.

## Upgrading

- **A managed install** updates from "System" in the admin, as
  [Updating](https://dhanabhon.github.io/tome-cms/running/updating/) describes, or with
  `sudo tome update` on the server. This release has one small migration,
  `034_default_category_name`, so the updater takes a full backup (database and media) before it
  applies it.
- **The new `tome`.** Updating the app does not replace the `tome` command on the server. To get
  the new `tome prune`, upgrade the updater from a v1.21.0 checkout once the app is on 1.21.0 (the
  updater stays at 1.6.0, and the site stays up):

  ```sh
  cd /opt/tome-cms-src
  git fetch --depth 1 origin tag v1.21.0
  git checkout --detach v1.21.0
  npm ci
  sudo npm run updater:upgrade -- --dry-run
  sudo npm run updater:upgrade
  ```

  Until then, `sudo tome prune` works as before and `--orphans` prints the usage.
- **A build from source** upgrades in place by running the deploy helper again; it runs the
  migration.
- **To go back**, restore the backup taken before the update.

`deploy/cloud-init.yaml` now installs 1.21.0.

## Added

- **Media files nothing points at.** `sudo tome prune` now also lists media files in storage that
  no image, copy, brand image or upload points at and that are more than a day old: how many, their
  size and the first 50 names. `sudo tome prune --orphans` deletes them. In a source checkout,
  `npm run media:cleanup -- --orphans` lists them, and `--orphans --execute` deletes them after you
  type a line that names the site, the database and the bucket. Such files are left behind by a
  crash in the middle of an upload, a failed delete, or images deleted under 1.19.x after a
  rollback; they also made `reset --execute` refuse the bucket, and its message now names the
  sweep.
  - **Never sweep a bucket another TomeCMS site uses**: its files look like nothing points at them.
    A managed server's bucket is its own.
  - **Not soon after restoring an older or database-only backup**: files uploaded after that backup
    count as nothing points at.
  - Every `tome prune`, the plain one included, now starts a short-lived app container for a few
    seconds.
- **A "Tome CLI" section in the documentation**, after "Running a site": an overview with every
  command, then status and logs, backups and restore, updates and clean-up, moving your writing,
  and themes and plugins, in English and Thai. The old `/running/cli/` address leads to it.

## Changed

- **The default category can be renamed** from the category manager (the name only). Its address
  stays `uncategorized`, it still has no page and cannot be deleted, and only it may be called
  "Uncategorized". After a rename, old `?category=Uncategorized` links show the whole home page.
  - `/api/v1` is unchanged. The admin API takes a name only for the default category; a different
    URL name or description answers 400 `default_category_fixed`, and naming another category
    "Uncategorized" answers 409 `name_reserved`.
  - Export writes the default category's name as `defaultCategory` in `manifest.json`. On import,
    posts in the archive's default category, by "Uncategorized", by the archive's name for it or
    by the site's own name for it, go into the site's default, which keeps its name. A 1.20.x
    importer does not know the field, so a renamed default becomes a category of its own there.
  - An MCP draft that names "Uncategorized" after a rename lands in the default category.
- **Paper's covers slider** tells the browser how wide it draws a cover on a phone (about a third
  wider than the screen, where it crops to 4:3), so phones load a copy sharp enough for it.

## Fixed

- **`tome import` that fails part-way** waits for the smaller copies of the pictures it had queued
  before it closes, instead of logging a failure for each.

## Testing

- **Unit:** what the sweep keeps and deletes (exactly a day old, younger, no date, tracked, another
  app's file), its confirmation line, the Paper slider's `sizes` and the CSS it follows, the import
  plan for a renamed default.
- **Integration:** migration 034 up and down (the trigger and the name check restored as they
  were); renaming the default allowed and every other change refused by the database; the sweep
  against real storage (an original, a copy, a brand image, a pending upload, an old and a young
  untracked file, another app's file; paging; a file coming into use while it runs; a failed
  delete); reset and the sweep reading one list of tracked files; `tome import` waiting for its
  copies; an MCP draft naming the old default.
- **Browser:** the installer end to end on an empty site, with a real passkey and nothing mocked,
  then what it wrote to the database and a second install refused; renaming "Uncategorized" in the
  category manager. The editor's selection test no longer races ProseMirror's 20 ms focus timer.
- **Operations:** the managed update with the migration, a fresh install, and a restore.

Malformed percent-escapes in an address (such as `/en/%E0%B8`) still answer `400 Bad request.`
from the Node server before TomeCMS runs. That is the right answer, it is never cached, and only
the development server answered 500.
