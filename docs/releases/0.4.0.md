# TomeCMS 0.4.0

Date: 2026-09-21
Status: Release candidate; not tagged for production

TomeCMS 0.4.0 is the 0.3.0 line with more of it in the owner's hands. A plugin can now reach
the page a reader sees, a theme is told more about how to draw it, a post can wait for a date,
a Thai title has a Thai address, an old address still reaches the article that moved from it,
and the editor can suggest -- through a plugin an installation chooses, never by default. This
is still a pre-1.0 clean-install line; the 0.2.0 release gates remain open.

## Upgrading

Three migrations landed after 0.3.0. An installation created from that candidate must run them
before starting:

```sh
npm run db:migrate
```

`017_scheduled_publishing` · `018_thai_slugs` · `019_content_redirects`

`018_thai_slugs` widens what the tables accept as an address. Its `down` narrows it again, and
is refused by the database while any Thai address exists -- going back would orphan every link
to one.

The admin names any of these it finds unapplied in a banner at the top of every screen, rather
than failing a save with a message that does not say why.

## For theme and plugin authors

Nothing a 0.3.0 theme or plugin relied on was taken away; each change below adds to a contract.

- `ThemeShellProps` and `ThemePostProps` carry `themeSettings`, the same record `ThemeHomeProps`
  already did. A theme setting reached only the homepage before, which was half an idea: a
  setting about articles, or about the header, had nowhere to arrive.
- A theme's `Shell` renders a named slot, `above`, before anything it draws. The core puts what
  is not the theme's there: a banner a plugin supplied the words for, and the mount points a
  plugin's browser code attaches to.
- Plugins declare two more hooks. `publicPage` has `siteNotice` -- a band of words, drawn by the
  core from what the plugin returns, never from markup it supplies -- and `publicClient`, which
  runs a plugin's own `client.ts` in readers' browsers. That is a larger grant than the sign-in
  hooks, and the contract says so: it is acceptable only because plugins ship in this repository
  and are reviewed in the same commit as everything else. `editorSuggestions` has
  `categoryLikelihoods` and `pickExcerpt`, described under Suggestions below.
- A plugin setting may be a `switch` (`on` or `off`) or a `color` (`#rrggbb` and nothing else),
  and a switch or colour declares a `fallback`. A colour lands in a style attribute on every
  public page, so the store refuses anything that is not only a colour rather than cleaning it,
  and the page checks it again before writing it.

## Highlights

### Plugins on the page a reader sees

- **Sticky Banner** puts a band across the top of every public page: a sentence in each
  language, in background and text colours the owner picks (black and white until then).
  Whether a reader can close it is the owner's choice. Closable, it slides up the way it would
  have been scrolled away, and is remembered by its words, so a new message is shown again to
  somebody who closed the last one; kept up, it has no close control and the page carries no
  script for it at all. A banner a reader closed is not drawn first and removed after -- a
  small blocking check in the head hides it before the first frame, the way the theme toggle
  already avoided its flash. A link typed into its settings is kept only if it is same-origin
  or `https`, so `javascript:` in that field cannot become a link on every page.
- **Image lightbox** opens an article's images full size in the element the platform already
  has for this, `<dialog>`. It asks for `article img` rather than one theme's class names --
  the first version read `paper`'s and found nothing in `plain`, and nothing in any article
  whose only image was its cover. Each image is reachable from a keyboard.
- A plugin that is off ships nothing: no markup, no stylesheet and no JavaScript. Each one's
  browser code is a chunk behind a dynamic import that only a mount point on the page asks for.
- The Cloudflare Turnstile card wears Cloudflare's own mark.

### What a theme can be told

`paper` declares seven settings now, adding two to the five 0.3.0 had:

- **A reading progress bar** across the top of an article, filling as the reader goes down it.
  It is drawn by a scroll timeline, so the page carries no handler and no script for it, and
  what moves is a transform. A browser without scroll-driven animations gets no bar rather than
  one stuck at zero. Off until it is asked for.
- **A header that stays in view**: sticky rather than fixed, so nothing below it is pushed down
  by the height of something that left the page, with a background of its own and under the
  progress bar. Off until it is asked for.

### Publishing and addresses

- **A post or page can be published for a date that has not come.** The date is a field in the
  settings drawer, in the owner's own clock, and the list says *Scheduled* rather than
  *Published* over an article nobody can read yet. Until the date arrives the article is not in
  the feed, not at its own address, not in the sitemap, not an hreflang target, not behind a
  category and not a menu item. What "published" means to a reader is written once, in
  `live()`; it had been six copies of `status = 'published'`, which is how one of them comes to
  disagree with the others.
- **A Thai title has a Thai address.** `slugify` had nothing for Thai, so a Thai title became an
  empty string and then `post-a1b2c3d4`, and a mixed one kept only its English. Addresses keep
  Thai now, a word between each pair of hyphens -- ICU's words, because Thai is written without
  spaces between them. The rule that a slug is `[a-z0-9]` was written three times, and the
  third, a constraint on the tables, was found only by asking the real stack for a Thai address.
  Every existing address stays exactly where it is.
- **An old address sends a reader on, permanently.** A published article's previous addresses
  are recorded by the tables themselves as it is renamed, and answered with a 301 to where it is
  now. They point at the article rather than at an address, so a chain of renames has no chain
  in it and no loop, and deleting the article takes them with it. A live article always wins
  over a forwarding address to the same place.
- **Redirects**, under Content, lists every old address with the article it reaches and whether
  a reader arrives there today. Each can be removed, and one can be added by hand -- for an
  address that changed before any of this was recorded.
- A card's fallback line was the first 157 characters, which in Thai cuts inside a word almost
  every time. It ends at a sentence now, or at a word when the first sentence is already too
  long, which for a Thai paragraph is the usual case.

### Suggestions while writing

The settings drawers can suggest categories for an article and a line from it for the excerpt,
through the **TypeSafe** plugin -- off until an owner switches it on under Appearance → Plugins
and gives it a key. An installation that does not use it draws no suggestion buttons at all.

The split between the plugin and the core is the point. The plugin supplies judgements and owns
how TypeSafe is asked. The core keeps everything that decides what reaches the owner and the
page:

- A category comes back as a likelihood, and the core decides the band: at or above 0.7 it is
  suggested, between 0.3 and 0.7 it is offered apart as *Perhaps*, below that it is not shown.
  One line at 0.6 had made 0.59 invisible and given 0.61 the same standing as 0.99.
- An excerpt comes back as a choice among passages the core found in the article, and is kept
  only if it is one of them -- so no plugin can put words on a card the owner did not write.
  Thai needed its own idea of a sentence: ICU reads a whole Thai paragraph as one, so a space
  with Thai on both sides is a break, except before `ๆ` or `ฯ` and around an English term set
  into the clause.
- Nothing is applied. A category is a chip to press; a line is a quotation with its own button,
  and does not replace what is in the field until it is pressed.
- A service that did not answer says so. It had been shown as "no line in the article works on
  its own", a judgement about the owner's writing that nobody made. The plugin also waits out
  a burst of 429, 503 or 529 the way the service asks, inside the one deadline the owner is
  already waiting on.

### The admin

- The drawers -- a post's settings, a page's, a plugin's setup, a theme's customize -- slide in
  from the edge they live on and leave the same way, and a click on the page behind closes
  them. The slide in is a keyframe with no fill on purpose: a transform left behind is a
  containing block, and the menus inside these drawers are positioned against the window so a
  scrolling panel cannot clip them.
- The block menus draw their icons from the admin's set; the slash menu had typed `H2`, a bullet
  and a curly quote.
- The editor no longer draws a closing quotation mark after the last character of a quote,
  where the caret could never stand. It read as a cursor stuck behind the mark, and as being
  unable to leave a quote at all.

## Validation boundary

The same gates as 0.3.0, and more of what they cover is driven rather than written: the editor
has browser tests that type into it, a switch in Customize is ticked and unticked rather than
set in the database, and a scheduled post is scheduled through the form. Each new guard was
checked by putting back the bug it guards against, and several first drafts were found to pass
without the fix they claimed -- those were rewritten or removed.

What is still required before a production tag is unchanged from the
[0.3.0 notes](0.3.0.md#still-required-before-a-production-tag).
