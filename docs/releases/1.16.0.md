# TomeCMS 1.16.0

Date: 2026-10-05
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.16.0 keeps each public page it has drawn in memory, so the next reader of the same
address is answered without the database. An edit still shows at once. It also carries a few search
and accessibility fixes. `/api/v1` is unchanged.

## Upgrading

- **A managed install** updates from "System" in the admin, as
  [Updating](https://dhanabhon.github.io/tome-cms/running/updating/) describes, or with
  `sudo tome update` on the server. There is no migration, so the updater backs up the database
  alone.
- **A build from source** upgrades in place by running the deploy helper again.
- **The updater** stays at 1.6.0. Nothing to upgrade on the server.

`deploy/cloud-init.yaml` now installs 1.16.0.

## Added

**The page cache.**

**What is kept:**
- the home pages, with a category or a later page;
- posts and pages;
- the feed, the sitemap and `robots.txt`.

**What is never kept:**
- a search;
- the admin, the API and media;
- anything while the site is closed for maintenance.

**When it empties at once:**
- every change saved in the admin;
- every draft an AI writes through MCP.

**When it expires on its own:**
- a scheduled post or page going public, and a home slide starting or ending;
- whatever happens, nothing is kept longer than five minutes.

**Two writes outside the app** show within those five minutes, because the app does not see them:
- posts brought in with `sudo tome import`;
- a plugin switched off with `scripts/plugin-disable.ts`.

**Limits.** The cache is capped at 32 MB of memory, counting each page's real size, so a flood of
odd addresses cannot grow it.

**Browsers.** A browser that already has a page gets a short `304` instead of the whole page.

**What changed on the wire.**
- Every answer from the cache carries `X-Tome-Cache: hit` or `miss`. To check that it works:

  ```sh
  curl -s -o /dev/null -D - https://cms.example.com/en | grep -i x-tome-cache
  ```

  The first answer says `miss`, the next `hit`.
- A cached page is sent with `Cache-Control: no-cache` and an `ETag`.
- A `HEAD` request is answered from a page already kept, but never fills the cache.

**How much faster.** Measured on a development machine with a production build, the client on the
same machine, `ab -c4 -n200`, the median of three runs:

| Page | 1.15.0 | 1.16.0 | Ratio |
| --- | ---: | ---: | ---: |
| Home | 776 req/s | 4,894 req/s | 6.3× |
| Post | 1,110 req/s | 5,422 req/s | 4.9× |

- **A hit:** answered in about a millisecond.
- **The first request after a change, or after a page expires:** 7 to 12 ms, a little more than a
  plain render took in 1.15.0, because it also works out when the page must expire and keeps it.
- **On a real server:** the numbers will differ; the test VPS is the measurement that counts.
- **Details:** in `docs/research/2026-10-04-page-cache-measurement.md`.

## Changed

- A post or page with a meta title of its own is titled by it exactly as written. The site's name
  used to be added after it, so a 70-character meta title became one of 87 that search results cut
  short. `og:title` and `twitter:title` follow it. A post or page without a meta title is titled as
  before.
- The home pages name the default language's home as `x-default`, as posts and pages already did.
- An article's cover carries the alt text its picture has in the media library, on Paper, Plain and
  Almanac, and in the admin's draft preview. A picture without alt text is decoration, as before.

## For theme authors

- A theme must draw the same HTML for every reader of an address, because the page is kept and
  shown to the next reader. It may not read cookies or request headers. Nothing in the bundled
  themes did.
- `coverImage` is a new optional field a theme's post receives, with the cover's alt text. A theme
  that ignores it works as before.

## Testing

- **Unit:**
  - **The cache:**
    - its key: only `category` and `cursor`, and only on the home page;
    - the size cap at real cost;
    - the expiry;
    - the race with an edit;
    - weak `ETag`s;
    - `HEAD`;
    - a response that may not be kept passing through untouched.
  - **The middleware:** an admin write clears the cache; the stats beacon and sign-in do not.
- **Integration:**
  - the next scheduled moment across posts, pages and home slides;
  - an MCP write clearing the cache;
  - the menu and slides snapshots ending with the page cache.
- **Browser:**
  - **The new spec:**
    - a miss and then a hit;
    - an admin rename shown at once;
    - a scheduled post appearing on a cached home page;
    - maintenance keeping nothing.

    Each step was proved to fail with its fix taken out.
  - **The existing specs:** eight that write to the database directly now clear the cache through
    an admin write.
