# TomeCMS 0.12.1

Date: 2026-09-26
Status: Release candidate; tagged and published as a GitHub release, not for production

TomeCMS 0.12.1 is 0.12.0 plus fixes, as the freeze before 1.0.0 asks. It is also the first
version tagged and published as a GitHub release. An install's "System" screen checks the
official repository for the latest release, and until now there was none to find.

This is still a pre-1.0 release candidate. A 0.x site upgrades in place when the deploy helper
is run again from a newer checkout.

## Upgrading

Migration `026_planned_dates` adds a `planned_at` column to posts and pages. The deploy helper
runs it with the others. There is no new setting and no new runtime dependency.

An installation created from a version earlier than 0.11.0 still needs what the
[0.11.0 notes](0.11.0.md#upgrading) list.

## Checking for an update

The "System" screen asks GitHub for the official repository's latest release. It takes a
release only when the release is published, not a prerelease, immutable, and carries an
`update-manifest.json` whose digest and version match its tag. From this version on, tagging
`vX.Y.Z` builds one through `release.yml`. A site on 0.12.0 now reads "TomeCMS 0.12.1 is
available." there, and a site on 0.12.1 reads that it is up to date.

The screen now tells three failed checks apart, each in the admin's language:

- No official release has been published yet, which GitHub answers with 404. It is not drawn
  as an error.
- GitHub could not be reached, did not answer within its deadline, or answered with an error,
  including a rate limit.
- GitHub answered, but the release, its digest or its manifest did not pass the checks.

A seventh "Check again" within ten minutes, and a check that runs past its deadline, are
worded in the admin's language too, instead of showing the server's English. The API's
`message` stays English for API callers, and a new `reason` field carries `no-release`,
`unreachable` or `unusable`.

The release workflow now reads the manifest's target migration from the migrations themselves.
It used to name `008_update_rate_limit_actions` whatever the release held. The GitHub release
carries the version's notes from this directory instead of a list of every commit.

The admin still cannot install an update. That arrives with the managed install at 1.0.0.

## A draft keeps its date

The "Publish at" date an owner chose on a draft was dropped by the save that filed the draft,
because a draft has no `published_at`, and the field was empty the next time the editor opened.
Migration 026 gives the plan a column of its own, `planned_at`, which only a draft carries; a
check constraint holds that. Publishing from the editor spends it as the publication date. An
emptied field empties it. "Publish" in the posts or pages list still means now, and drops a
planned date, as it always published at once.

`published_at` keeps its meaning, so the redirects, the lists and every public query read it as
before.

## Words in the admin's language

- The language tabs on Maintenance, Home slides and Navigation open on the owner's language.
  They used to open on Thai. A new menu item's default label is Home in the language of the
  menu being edited.
- A spare Passkey's suggested name, and the recovery page's refusal of a code, are admin copy.
  The recovery page words its refusal from the answer's status: a wrong or used code, too many
  tries, or the server.
- The library says a file is still used, and how many times, from the places the server already
  names.
- Every dialog now needs its caller to name its buttons, so `astro check` refuses one that
  names none. The link prompt, the upload alert and six confirmations fell back to an English
  "Cancel" or "OK". The update install confirmation keeps its English title, message and button,
  since managed updates start at 1.0.0.
- The editor's language chips say Scheduled for an edition published with a date still to come,
  as the lists do.
- A popup whose words are the other language's draws its default decline button and its close
  label in that language, with its words.

## Other fixes

- A closable notice band from any plugin can be closed. The plugin contract gives the band's
  dismissal to the core, but the close code came only with the Notice plugin.
- The first-run bootstrap should now run on Windows. It starts npm through `npm.cmd` in a shell,
  with a fixed command, and skips the check that only the owner can read `.env.local`, because
  Windows reports every writable file as readable by everyone. It has not yet been tried on a
  Windows machine.
- An article that opens with a video fetches the video's poster first, as one that opens with a
  picture already did.

## For theme authors, plugin authors and headless sites

- The core closes a notice band that has a `dismissKey`, and remembers that it was closed, from
  `NoticeScript`. A plugin's `siteNotice` needs no browser code. The Notice plugin no longer has
  a `publicClient`.
- In the admin API, a post and a page carry `planned_at`, an ISO date or `null`. The public API
  and its serializers are unchanged.
- The editor's translation summaries carry `published_at`.

## Validation boundary

The integration and browser runs are from `6a013ea`, the merge of the fixes. This release changes
only the version, the documentation and `release.yml` on top of it, and the check and unit runs are
from the release commit itself.

- `npm run check`: `astro check` with no error and no warning, and the scripts' self-tests.
- `npm run test:unit`: 565 tests, all passing.
- `npm run test:integration`: 60 tests in 40 runs against a real PostgreSQL and object store,
  all passing. A new test covers a draft's planned date through every write, and the check
  constraint refusing a published row with a plan.
- `npm run test:e2e`: 136 tests on the desktop and phone projects, 91 passing, 43 skipped (the
  specs that run on the desktop project only) and 2 failing in the full run. Both passed alone:
  the alignment test in `editor-blocks.spec.ts`, a known flake, and "a select opens clear of the
  dialog it lives in" in `select-in-dialog.spec.ts`, three times out of three. Neither was
  changed by this release. In CI, "the formatting bar is whole" failed once and passed on the
  rerun.
- The update check was run against a release shaped as `release.yml` builds it, with the
  manifest this workflow generates: a 0.12.0 site read 0.12.1 as available, and a 0.12.1 site
  read itself as up to date.
- The documentation site: `npm --prefix website run check` found every page's twin and no
  listed mark.

0.12.1 has not yet been installed on the two real HTTPS servers, `linux/amd64` and
`linux/arm64`, that the [road to 1.0.0](../plans/2026-09-24-road-to-1.0.0.md) names. That is
still to be done before 1.0.0. What is required before a production tag is unchanged from the
[0.3.0 notes](0.3.0.md#still-required-before-a-production-tag).
