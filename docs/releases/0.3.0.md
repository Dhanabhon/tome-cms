# TomeCMS 0.3.0

Date: 2026-09-20
Status: Release candidate; not tagged for production

TomeCMS 0.3.0 keeps the 0.2.0 core and rebuilds what is on top of it. The public site becomes
one theme among others, plugins can fill hooks the core declares, the admin is redrawn on one
set of surfaces, and both the site and the admin read in the language they are being read in.
This is still a pre-1.0 clean-install line; the 0.2.0 release gates remain open.

## Upgrading

Six migrations landed after 0.2.0 was prepared. Any installation created from that candidate
must run them before starting:

```sh
npm run db:migrate
```

`008_update_rate_limit_actions` · `009_site_theme` · `010_visitor_theme_choice` ·
`011_powered_by` · `012_site_theme` · `013_plugin_settings`

## Breaking changes

- The public templates moved out of `src/components/blog/` into `src/themes/paper/parts/`.
  `SEOHead.astro` stayed, because it belongs to the document head rather than to a theme. A
  fork that imported those paths must repoint them.
- The public half of `src/styles/global.css` moved into `src/themes/paper/theme.css`. The core
  stylesheet keeps the tokens, both colour schemes, the resets, the focus ring and the two
  rules both sides draw; anything only a reader sees now belongs to the theme drawing it.
- Settings stops calling two different things a theme, and stops holding either. Both moved
  to **Appearance → Themes**, a screen of their own: **Theme** is the one that draws the site,
  and the light/dark setting keeps the name **Appearance**. `/admin/plugins` is unchanged; a
  sub-menu is a fact about the sidebar, not about the URL. The stored columns are unchanged.
- `src/lib/admin-icons.ts` is `src/lib/icons.ts`, and `components/admin/AdminIcon.*` are
  `components/Icon.*`: the public site draws from the same set.

## Highlights

### Themes

- The public site is a theme: templates and CSS behind a typed contract, chosen under **Appearance
  → Themes**. Appearance is the admin's third section, after what the site publishes and how the
  installation is set up: it holds the two screens that decide what a reader meets. It folds,
  and is the sidebar's first nesting. A `<details>` does it, so the keyboard, the ARIA and
  the open state are the browser's rather than ours, and the section arrives open on the
  screens it holds -- nothing is stored to remember which way it was left.
  `paper` is the look TomeCMS ships with; `plain` is a deliberately spare second one.
- A theme owns the templates and the stylesheet and nothing else. Routing, queries, the
  document head and its SEO, the fonts and the design tokens stay in core, so a theme can be
  plain but not wrong or slow.
- Each theme is a dynamic import and links its own stylesheet, so a reader is served the look
  the owner chose and nothing of the ones they did not.

### Plugins

- A plugin fills hooks the core declares. There are two, both on the admin sign-in: what to put
  in the form, and what to make of an attempt. No routes, no database, no startup code.
- Plugins ship in the repository and are switched on and configured under **Appearance →
  Plugins**. A setting marked `secret` is encrypted at rest with `TOME_CMS_CONTEXT_SECRET` and
  never sent to a browser; the screen is told only whether one is set.
- The first plugin is **Cloudflare Turnstile**. A plugin reports what it found and the core
  decides what that means: an invalid, missing or spent token refuses the attempt, while a
  wrong secret key, a malformed request, an unreachable Cloudflare or a timeout lets it
  through and is logged. Mistyping a secret key cannot lock the owner out.
- The guard runs on the sign-in attempt and never on registration, so the recovery path stays
  open with a plugin on, misconfigured, or both. `npm run plugin:disable <id>` switches one off
  from a shell, with `--forget` to clear its settings.

### The site a reader meets

- The homepage is a grid of cards with category filters that swap the list in place, six posts
  to start and a row at a time after.
- The homepage, the article page, the header and the footer read in the reader's language. A
  Thai page dates its posts and its copyright line on the same calendar.
- The footer can credit TomeCMS, and the owner can switch that off. A site that never wrote a
  tagline is given one rather than meeting a reader with a gap.
- Visitors can be offered a light/dark control, or not: switching it off makes the site's own
  setting the only one, ignores a stale choice in a visitor's browser, and sends no script.

### The admin

- Every screen stands in one frame on one card surface: the story lists, the file library, the
  menu editor, categories, the form screens, both editors and their drawers, and the sign-in.
- One icon set, one badge, one row menu, one set of tabs, one status pill.
- Every control that starts a request says so, and says it without moving: a busy button wears
  its spinner over its own label.
- Failures name their cause in the owner's language rather than repeating the server's English.

### Design system

- The system is repainted in paper, ink and a single green family. Google Sans carries the
  display roles and IBM Plex Sans Thai keeps the interface; the type scale stopped being two
  scales.
- `src/styles/installer-tokens.css` remains the source of truth, and `npm run check` still
  fails the build when this document or `tailwind.config.mjs` drifts from it.

### Passkeys and recovery

- A sign-in offers only the Passkeys this installation knows. Without that list a browser
  offered every Passkey it held for the hostname, and choosing one left over from an earlier
  installation was answered with a bare 401.
- A recovery no longer excludes the Passkey it is replacing. The record of a lost Passkey was
  refusing to let its own replacement be made.
- 401 on a sign-in means the credential is unknown, not that a session expired; an
  authenticator that already holds a Passkey for this account says which device the spare
  belongs on. Neither is described as the other any more.
- A Passkey is marked used when it verifies, rather than when its signature counter moves. A
  Passkey synced through a password manager reports a counter of zero for life, so the
  Security screen said "never used" about the key its owner signs in with every day.

### Operations

- `npm run admin:recover -- --execute` issues the single-use recovery link the recovery page
  already offered. It reads `.env.local`, `/etc/tome-cms/tome-cms.env`, or `TOME_CMS_ENV_FILE`.
- Managed updates were hardened through the release-revalidation, rate-limit, deployment and
  rollback paths.
- `npm run css:snapshot` and `npm run css:diff` report which selectors a build serves, which is
  how the split between the core stylesheet and a theme's own is kept where it is.

## Validation boundary

`npm run check` reports no errors or warnings and `npm run test:unit` is green for this
candidate.

### The dependency audit

The audit the 0.2.0 notes made a blocker has been rerun, and the part of it that could be
closed is closed. `npm audit --omit=dev` reports **no critical and no high advisories**, where
0.2.0 had one of each.

- Astro 5.18 to 7.3.3, with `@astrojs/node` 9 to 11 and `@astrojs/react` 4 to 6. This clears
  ten Astro advisories including the critical one, the esbuild advisory, and the high Sharp
  advisory that came with Astro's own bundled copy.
- `@astrojs/tailwind` is gone. It peers on Astro 3 to 5 and was never more than a PostCSS
  config; Tailwind's own configuration is unchanged.
- Node's floor rises to 22.12.0, which Astro 7 requires. `node:22-alpine` already satisfies it.

**Thirty-eight moderate advisories remain, and none of them is ours to close.** Every one is
`@tiptap/core <= 3.30.3` or a package depending on it. The patched release is 3.31.3, but the
editor is `novel`, whose current version — 1.0.2, the latest published — depends on
`@tiptap/core ^2.11.2` and eighteen other Tiptap 2 packages. Moving to a patched Tiptap means
either novel publishing a Tiptap 3 line or replacing novel with Tiptap 3 wired directly.
That is a separate piece of work with its own editor-behaviour risk, and it is the last thing
standing between this line and a clean production audit.

### The test gates

Run against Astro 7, all green:

| Gate | Result |
|---|---|
| `npm run test:unit` | 384 pass |
| `npm run test:integration` | 15 files, every test passing, against disposable PostgreSQL and SeaweedFS |
| `npm run test:e2e` | the installer acceptance and a Passkey sign-in round trip pass on desktop Chromium; the mobile project skips itself, because virtual WebAuthn is Chromium-only |
| `npm run test:operations` | pass |
| `npm run test:operations:update` | 9 tests, the managed 1.0.0 to 1.0.1 update isolated, recoverable and preserving infrastructure |

Three things had to be repaired before the browser gate could run at all, and two of them were
already broken before this release:

- `astro dev` moved from `node_modules/astro/astro.js` to `node_modules/astro/bin/astro.mjs`.
- Astro 7 allows one dev server per project root, and this suite runs two on purpose. The
  installer's own server now passes `--ignore-lock`.
- The installer acceptance had been failing since 2026-09-13, when `feat(ops): operate
  postgres and s3 deployments` made object storage a real check and left the test expecting
  it to report "Deferred". The wizard had been telling people the same thing: *"Storage is
  intentionally marked deferred and does not block this setup"*, in both languages, about a
  check that does block it. Both now say what is true.

The browser gate also now runs in CI, and covers signing in. Until 2026-09-20 it ran nowhere
and covered only installation, which is how a sign-in that could never succeed passed the
type checker, the unit suite, the build and the integration suite on its way out.
`tests/e2e/passkey-sign-in.spec.ts` registers a Passkey through the real recovery flow against
a disposable database, signs out, and signs back in. Reintroducing the fault fails it.

Both projects are Chromium, and the suite skips its mobile one before a browser is launched
rather than inside a test that has already got one. The first CI run of the gate failed on
that: the mobile project was an iPhone, which is WebKit, and CI installs only the browser the
suite needs. It had passed locally, where a WebKit had been downloaded long ago.

Astro 7 also backgrounds the dev server when it detects that an agent is running the command,
which leaves Playwright watching a process that has already exited. The Playwright config and
the spec set `ASTRO_DEV_BACKGROUND` so the server stays attached whoever starts it.

### Still required before a production tag

Public immutable release and attestation verification, and real `amd64`/`arm64` HTTPS VPS
acceptance. Both need infrastructure this repository cannot stand up for itself.

One thing in this release has not been exercised against the live service it talks to:
Cloudflare Turnstile has been verified against Cloudflare's documented test keys and against a
Cloudflare made unreachable, but not with a real site key on a real hostname.
