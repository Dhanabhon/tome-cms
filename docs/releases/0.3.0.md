# TomeCMS 0.3.0

Date: 2026-09-20
Status: Release candidate; not tagged for production

TomeCMS 0.3.0 keeps the 0.2.0 core and rebuilds what is on top of it. The public site becomes
one theme among others, plugins can fill hooks the core declares, the admin is redrawn on one
set of surfaces, and both the site and the admin read in the language they are being read in.
This is still a pre-1.0 clean-install line; the 0.2.0 release gates remain open.

## Upgrading

Six migrations landed after 0.2.0 was prepared. Any installation created from that candidate
must run them before starting:

```sh
npm run db:migrate
```

`008_update_rate_limit_actions` · `009_site_theme` · `010_visitor_theme_choice` ·
`011_powered_by` · `012_site_theme` · `013_plugin_settings` · `014_post_excerpt` ·
`015_page_excerpt` · `016_theme_settings`

## Breaking changes

- The public templates moved out of `src/components/blog/` into `src/themes/paper/parts/`.
  `SEOHead.astro` stayed, because it belongs to the document head rather than to a theme. A
  fork that imported those paths must repoint them.
- The public half of `src/styles/global.css` moved into `src/themes/paper/theme.css`. The core
  stylesheet keeps the tokens, both colour schemes, the resets, the focus ring and the two
  rules both sides draw; anything only a reader sees now belongs to the theme drawing it.
- Settings stops calling two different things a theme, and stops holding either. Both moved
  to **Appearance → Themes**, a screen of their own: **Theme** is the one that draws the site,
  and the light/dark setting keeps the name **Appearance**. `/admin/plugins` is unchanged; a
  sub-menu is a fact about the sidebar, not about the URL. The stored columns are unchanged.
- `src/lib/admin-icons.ts` is `src/lib/icons.ts`, and `components/admin/AdminIcon.*` are
  `components/Icon.*`: the public site draws from the same set.

## Highlights

### Themes

- The public site is a theme: templates and CSS behind a typed contract, chosen under **Appearance
  → Themes**. Appearance is the admin's third section, after what the site publishes and how the
  installation is set up: it holds the two screens that decide what a reader meets. It folds,
  and is the sidebar's first nesting. A `<details>` does it, so the keyboard, the ARIA and
  the open state are the browser's rather than ours, and the section arrives open on the
  screens it holds -- nothing is stored to remember which way it was left.
  `paper` is the look TomeCMS ships with; `plain` is a deliberately spare second one.
- A theme owns the templates and the stylesheet and nothing else. Routing, queries, the
  document head and its SEO, the fonts and the design tokens stay in core, so a theme can be
  plain but not wrong or slow.
- Each theme is a dynamic import and links its own stylesheet, so a reader is served the look
  the owner chose and nothing of the ones they did not.
- A theme declares its own settings, the way a plugin does, and the one in use gains
  **Customize** on its card -- the button the reference screen has and this one left out
  until there was something behind it. The core renders the form from the declaration and
  stores the answers keyed by theme, so switching away and back returns the owner to the
  choices they made rather than to the defaults.
- `paper` declares five: the hero and its headline, how many cards go across, how many posts
  a load holds, and whether rows arrive as the reader nears the end. Six posts was a constant in the homepage route with a comment explaining
  that six ends on a full row at one, two or three cards across -- true of a three-column
  grid and meaningless to a one-column list, which is why it is the theme's to say. The
  choices are 6, 12 and 18 for that reason: the rule is in the control rather than in a
  number an owner can get wrong.
- Turning the second off leaves the link to older posts that a reader without JavaScript
  already follows, and the feed's code is not downloaded. It was, at first: a static import
  puts the feed inside the page's own script, so switching the setting off changed the markup
  and not the bytes -- measured rather than assumed, by watching what the page requested in
  both states. The import is dynamic now, which makes the feed a chunk of its own in the
  build, and a test fails if a static one comes back.
- The hero can be hidden, shown, or shown with one reveal on arrival -- declared only inside
  `prefers-reduced-motion: no-preference`, so a reader who asked for less motion gets none
  rather than one turned off again afterwards. It reuses the keyframes a card settles in
  with, because two copies of a rule are two rules that drift.
- A third hero shows the covers of the newest posts, from the page the route already
  fetched -- no extra query, and a post that gains a cover is in it without being told. The
  track scrolls and snaps natively, so it works by swipe, wheel and keyboard with no script;
  what the script adds is the rotation, and the button that stops it. It never starts for a
  reader who asked for less motion, it stops while a pointer or the keyboard is inside it,
  the first image is eager at high priority and the rest are not asked for at all, and a
  homepage whose newest posts have no covers falls back to text rather than standing empty.
- The cards slide in, a beat behind each other across the row, and the slide is transform
  only. An element at opacity 0 has not been painted, so fading the first row in would hold
  the largest contentful paint back by the length of the animation; a card that slides is
  painted where it starts. The cards the feed appends keep their fade, being nobody's
  largest paint.
- Its headline is the owner's, and a blank one is the theme's in the language the page is
  being read in. It was a single English sentence written into the template, so a Thai reader
  met the homepage in English -- visible in this release's own theme screenshots. Sixty
  characters, and a headline with no break opportunity in it breaks anyway rather than
  running out of the band.
- That headline is the first setting of kind `text`, which is also the first refusal that had
  to say why properly: a value too long is not a value "this theme does not offer", and
  sending an owner to look for a list that does not exist is its own small failure.
- Cards across is asked for rather than fixed: two, three or four at the widest, and fewer
  wherever that many cannot be read. A track is at least a share of the row, which caps the
  count, and never narrower than a floor, which uncaps it again on a narrow screen -- so a
  site asking for four is still one across on a phone. Four on an 80rem page works out at
  18.9rem a card, just under the floor the other two keep, so choosing four is also choosing
  that much less room per title. Three is what the grid did before it could be asked, and
  still is.
- A value a theme no longer offers is not served either -- a release that drops a choice, or
  a row edited by hand, falls back to what the theme declared.
- The screen is a grid of cards, and each card shows its theme drawing this installation's own
  posts. The frame is `/admin/themes/preview/<id>`: the homepage route with the theme taken
  from the URL rather than the settings, behind the owner's session, `noindex`, and refused
  for an id that names no installed theme. It is a picture and not a control -- no pointer, and
  out of the tab order -- so the only thing to press on a card is the button that applies it.
  Nothing is committed beside a theme to stand in for it, which is the arrangement in which a
  theme's picture and the theme come to disagree.
- Choosing a theme applies it, and so does every other control on the screen. There is no save
  button there and nothing to leave unsaved.

### Plugins

- A plugin fills hooks the core declares. There are two, both on the admin sign-in: what to put
  in the form, and what to make of an attempt. No routes, no database, no startup code.
- Plugins ship in the repository and are switched on and configured under **Appearance →
  Plugins**. A setting marked `secret` is encrypted at rest with `TOME_CMS_CONTEXT_SECRET` and
  never sent to a browser; the screen is told only whether one is set.
- The first plugin is **Cloudflare Turnstile**. A plugin reports what it found and the core
  decides what that means: an invalid, missing or spent token refuses the attempt, while a
  wrong secret key, a malformed request, an unreachable Cloudflare or a timeout lets it
  through and is logged. Mistyping a secret key cannot lock the owner out.
- The guard runs on the sign-in attempt and never on registration, so the recovery path stays
  open with a plugin on, misconfigured, or both. `npm run plugin:disable <id>` switches one off
  from a shell, with `--forget` to clear its settings. The screen says so, where the owner is
  deciding whether to switch one on.
- The screen is a card per plugin. A plugin directory fills the band under a card with stars,
  install counts and a compatibility line; there is nothing here to put there, because plugins
  ship with the release and there is nothing to compare them against. Inventing any of it
  would be data that is not true, so the band says what a directory could not know instead:
  which of the core's hooks this plugin fills. A manifest names a hook from a closed set the
  core owns and the core supplies the words, and a test holds each plugin to what it named.
- A manifest also names its icon, from the admin's own set. A plugin has no way to put an
  image on the screen, which keeps the grid to one drawing style.
- The switch on a card applies on the spot and says in a word which way it is thrown -- no two
  surfaces in this palette are far enough apart for a background to mean anything. A plugin
  that is not set up cannot be switched on there, which is the refusal the server was already
  making; the reason is said in the panel where the fix is, rather than beside a control that
  already reads "not set up yet".
- The fields moved into the panel the editors already use for a panel of fields, opened the way
  they open it: focus to the close button, Escape closes, focus returns.
- A write to a plugin keeps a setting it was not given. Before this, a blank secret was kept
  and an unmentioned text setting was erased, so a request that only switched a plugin on
  would take its site key with it. `writePluginSettings` had no test at all; it has one now,
  and reintroducing the old behaviour fails it.

### The site a reader meets

- The public header is two zones, not three: the site's name on the left, and everything a
  reader can act on -- the menu, the light/dark control, the language button -- gathered on
  the right. The menu was centred in a box that already reached the language button, so the
  gap a reader saw was inside that box rather than between it and anything, and the optical
  centre of a row with a long wordmark at one end and a pill at the other is not its middle.
- The language switcher stopped placing itself. It carried its own `order`, `flex` and auto
  margin and reset them again in a media query, so where it sat depended on whether the core
  stylesheet or its own scoped style was injected last -- and moving the header's rules into
  the theme, where they belong, changed that answer and moved the button. The theme's header
  says where its children go; the component styles only itself. Its installer variant still
  places itself, because that variant exists to fit one particular header.
- A post has an excerpt of its own: the line its card shows, written for a reader deciding
  what to open. The card was drawing the search description, so one sentence was serving two
  readers and changing either one changed the other. A post that has no excerpt keeps showing
  what it showed before -- the search description, then the opening of the post -- so nothing
  a site already publishes changes until someone writes one.
- A page carries the same field on the same terms. Nothing TomeCMS ships renders it -- there
  is no grid of pages the way there is a grid of posts -- so it is there for a theme that
  lists or links to pages, and the field says as much rather than implying a card exists.
- An excerpt is never what a post tells a search engine. One function answered both questions
  at first, and `<meta name="description">` on the article page called it, so writing a line
  for a card silently replaced the line written for a search result -- the confusion the
  field exists to end, rebuilt one level down. `postDescription` and `postExcerpt` are
  separate now, with `pageDescription` and `pageExcerpt` matching them.
- It is bounded at 120 characters, in the field and in the column. The card clamps to two
  lines, and two lines hold between 76 and 108 characters depending on how wide the grid is
  -- measured on the rendered card at 1440, 1024 and 768, not estimated. 120 is where one
  sentence still fits and two do not.
- The homepage is a grid of cards with category filters that swap the list in place, six posts
  to start and a row at a time after.
- The homepage, the article page, the header and the footer read in the reader's language. A
  Thai page dates its posts and its copyright line on the same calendar.
- The footer can credit TomeCMS, and the owner can switch that off. A site that never wrote a
  tagline is given one rather than meeting a reader with a gap.
- Visitors can be offered a light/dark control, or not: switching it off makes the site's own
  setting the only one, ignores a stale choice in a visitor's browser, and sends no script.

### The admin

- A select opens clear of whatever it is inside. Its list was absolutely positioned, which
  puts it in the nearest scroll box -- and the menu dialog and the editors' drawers are both
  scroll boxes, so a list opened near the bottom of one was cut off at that box's edge, with
  the rest reachable only by scrolling the dialog under it. It is fixed now and placed
  against its trigger, opening upward when it does not fit below. `tests/e2e/select-in-dialog.spec.ts`
  measures the rendered list at three window heights; nothing before it could have, because
  the markup and the CSS are each right on their own and only wrong in a place they are put.
  Adding it needed the browser suite fixed first: Playwright runs every spec in one worker,
  the database client is a module singleton bound at import, and `closeDatabase()` destroys
  it for good -- so the second spec to want a database got a dead pool. Each spec that owns
  one now names itself in `tests/e2e/own-worker.ts` and is given a worker of its own.
- Every screen stands in one frame on one card surface: the story lists, the file library, the
  menu editor, categories, the form screens, both editors and their drawers, and the sign-in.
- One icon set, one badge, one row menu, one set of tabs, one status pill.
- Every control that starts a request says so, and says it without moving: a busy button wears
  its spinner over its own label.
- Failures name their cause in the owner's language rather than repeating the server's English.
- The admin says when the database is behind the build, above whatever screen the owner
  opened, and names the migrations that have not run. A build whose migrations are pending
  writes to columns that are not there, and the owner meets that as a save that failed for
  no stated reason -- which is how it was met on 2026-09-20, an hour after the excerpt column
  was added. `/health/ready` had been reporting it the whole time; nothing the owner looks at
  was asking. `tests/e2e/admin-migration-warning.spec.ts` removes an applied migration's row,
  which is what a build ahead of its database looks like from inside, and fails if the admin
  stays quiet.

### Design system

- The system is repainted in paper, ink and a single green family. Google Sans carries the
  display roles and IBM Plex Sans Thai keeps the interface; the type scale stopped being two
  scales.
- `src/styles/installer-tokens.css` remains the source of truth, and `npm run check` still
  fails the build when this document or `tailwind.config.mjs` drifts from it.

### Passkeys and recovery

- A sign-in offers only the Passkeys this installation knows. Without that list a browser
  offered every Passkey it held for the hostname, and choosing one left over from an earlier
  installation was answered with a bare 401.
- A recovery no longer excludes the Passkey it is replacing. The record of a lost Passkey was
  refusing to let its own replacement be made.
- 401 on a sign-in means the credential is unknown, not that a session expired; an
  authenticator that already holds a Passkey for this account says which device the spare
  belongs on. Neither is described as the other any more.
- A Passkey is marked used when it verifies, rather than when its signature counter moves. A
  Passkey synced through a password manager reports a counter of zero for life, so the
  Security screen said "never used" about the key its owner signs in with every day.

### Operations

- `npm run admin:recover -- --execute` issues the single-use recovery link the recovery page
  already offered. It reads `.env.local`, `/etc/tome-cms/tome-cms.env`, or `TOME_CMS_ENV_FILE`.
- Managed updates were hardened through the release-revalidation, rate-limit, deployment and
  rollback paths.
- `npm run css:snapshot` and `npm run css:diff` report which selectors a build serves, which is
  how the split between the core stylesheet and a theme's own is kept where it is.

## Validation boundary

`npm run check` reports no errors or warnings and `npm run test:unit` is green for this
candidate.

### The dependency audit

The audit the 0.2.0 notes made a blocker has been rerun, and the part of it that could be
closed is closed. `npm audit --omit=dev` reports **no critical and no high advisories**, where
0.2.0 had one of each.

- Astro 5.18 to 7.3.3, with `@astrojs/node` 9 to 11 and `@astrojs/react` 4 to 6. This clears
  ten Astro advisories including the critical one, the esbuild advisory, and the high Sharp
  advisory that came with Astro's own bundled copy.
- `@astrojs/tailwind` is gone. It peers on Astro 3 to 5 and was never more than a PostCSS
  config; Tailwind's own configuration is unchanged.
- Node's floor rises to 22.12.0, which Astro 7 requires. `node:22-alpine` already satisfies it.

**Thirty-eight moderate advisories remain, and none of them is ours to close.** Every one is
`@tiptap/core <= 3.30.3` or a package depending on it. The patched release is 3.31.3, but the
editor is `novel`, whose current version — 1.0.2, the latest published — depends on
`@tiptap/core ^2.11.2` and eighteen other Tiptap 2 packages. Moving to a patched Tiptap means
either novel publishing a Tiptap 3 line or replacing novel with Tiptap 3 wired directly.
That is a separate piece of work with its own editor-behaviour risk, and it is the last thing
standing between this line and a clean production audit.

### The test gates

Run against Astro 7, all green:

| Gate | Result |
|---|---|
| `npm run test:unit` | 384 pass |
| `npm run test:integration` | 15 files, every test passing, against disposable PostgreSQL and SeaweedFS |
| `npm run test:e2e` | the installer acceptance and a Passkey sign-in round trip pass on desktop Chromium; the mobile project skips itself, because virtual WebAuthn is Chromium-only |
| `npm run test:operations` | pass |
| `npm run test:operations:update` | 9 tests, the managed 1.0.0 to 1.0.1 update isolated, recoverable and preserving infrastructure |

Three things had to be repaired before the browser gate could run at all, and two of them were
already broken before this release:

- `astro dev` moved from `node_modules/astro/astro.js` to `node_modules/astro/bin/astro.mjs`.
- Astro 7 allows one dev server per project root, and this suite runs two on purpose. The
  installer's own server now passes `--ignore-lock`.
- The installer acceptance had been failing since 2026-09-13, when `feat(ops): operate
  postgres and s3 deployments` made object storage a real check and left the test expecting
  it to report "Deferred". The wizard had been telling people the same thing: *"Storage is
  intentionally marked deferred and does not block this setup"*, in both languages, about a
  check that does block it. Both now say what is true.

The browser gate also now runs in CI, and covers signing in. Until 2026-09-20 it ran nowhere
and covered only installation, which is how a sign-in that could never succeed passed the
type checker, the unit suite, the build and the integration suite on its way out.
`tests/e2e/passkey-sign-in.spec.ts` registers a Passkey through the real recovery flow against
a disposable database, signs out, and signs back in. Reintroducing the fault fails it.

Both projects are Chromium, and the suite skips its mobile one before a browser is launched
rather than inside a test that has already got one. The first CI run of the gate failed on
that: the mobile project was an iPhone, which is WebKit, and CI installs only the browser the
suite needs. It had passed locally, where a WebKit had been downloaded long ago.

Astro 7 also backgrounds the dev server when it detects that an agent is running the command,
which leaves Playwright watching a process that has already exited. The Playwright config and
the spec set `ASTRO_DEV_BACKGROUND` so the server stays attached whoever starts it.

### Still required before a production tag

Public immutable release and attestation verification, and real `amd64`/`arm64` HTTPS VPS
acceptance. Both need infrastructure this repository cannot stand up for itself.

One thing in this release has not been exercised against the live service it talks to:
Cloudflare Turnstile has been verified against Cloudflare's documented test keys and against a
Cloudflare made unreachable, but not with a real site key on a real hostname.
