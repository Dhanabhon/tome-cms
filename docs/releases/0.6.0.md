# TomeCMS 0.6.0

Date: 2026-09-21
Status: Release candidate; not tagged for production

TomeCMS 0.6.0 is 0.5.0 with the site's own logo, name and icon, and admin buttons that say
they are working the same way everywhere, for long enough to be seen. This is still a pre-1.0
clean-install line; the 0.2.0 release gates remain open.

## Upgrading

One migration landed after 0.5.0, and an installation created from it or from 0.4.0 must run
it before starting:

```sh
npm run db:migrate
```

`020_site_brand` adds four columns to `site_settings`: `brand_logo`, `brand_logo_dark` and
`brand_icon`, each null or an object, and `hide_site_name`. An installation created from 0.3.0
needs what the [0.4.0 notes](0.4.0.md#upgrading) list as well, and one from before that the
[0.3.0 notes](0.3.0.md#upgrading). The admin names any migration it finds unapplied in a
banner at the top of every screen.

Its `down` drops the four columns, and so forgets the logos and the icon. Their files stay in
the bucket, and have to be removed by hand before a reset, which refuses a bucket holding
objects it does not account for.

## For theme authors and headless sites

Nothing a 0.5.0 theme, plugin or API client relied on was taken away.

- `ThemeShellProps` gains `brand`: the logo, the dark logo and whether the name stands beside
  them. A theme draws it with the core's `<SiteBrand brand={brand} siteName={siteName} />`
  inside its home link, and sizes it with `--site-logo-height`; `paper` and `plain` both do. A
  theme that does not keeps drawing what it drew, and does not show the owner's logo.
- The rules are the core's, applied before a theme is called: the name leaves the header only
  while there is a logo to stand in for it, and a dark logo is drawn only beside a logo.
- `GET /api/v1/content/site` gains `brand` -- the logo and dark logo as `{ url, width, height,
  mimeType }`, the icon as `{ png32, png180, svg }`, and `showSiteName` -- so a site that uses
  TomeCMS headless can wear the same logo its bundled theme would draw. It is always present;
  a site without a logo says it has none. The OpenAPI document describes it.
- The object key grammar that backup, restore-check and reset accept gains `svg`, for these
  files alone. The media library's own types, and the checks on its tables, do not change.

## Highlights

### The site's own logo, name and icon

- Settings gains **Logo and icon**: a logo, an optional logo for the dark theme, and the
  site's icon. A logo is PNG, JPEG, WebP or SVG, an icon PNG or SVG, each under 1 MB, and a
  raster icon at least 180 × 180. The type is read from the bytes, never from the name.
- **An SVG is sanitized before it is stored.** Shapes, text, gradients, clip paths, masks and
  style are kept; script, `foreignObject`, links, embedded images, animation and every event
  handler go. References stay inside the file, and CSS loads nothing from outside it -- CSS
  with an escape in it is dropped whole, since an escape can spell `url(` without its letters.
  What is left must still be drawable, or the file is refused and the owner is told why. The
  site shows these files only through `<img>`; the sanitizing is for the file opened at its
  own address, where it is a document and the only guard.
- A raster logo is stored as it came. An icon is drawn at 32 and 180 pixels, for a tab and for
  a phone's home screen, centred on a transparent square rather than stretched; an SVG icon is
  kept as well, for the browsers that take one.
- The files go through the server, under a fresh key each time, so a changed logo is never
  served from a cache as the old one. An upload applies at once; a replacement deletes what it
  replaced, and a failure before the setting is written takes back what the request stored.
- The header of both themes wears the logo, and the name can be hidden behind it -- in the
  header alone. The name stays in the tab, in search results, in the footer and in the feed,
  and becomes the logo's text alternative, so the home link always has one. Taking the logo
  away brings the name back, whatever the switch still says.
- **A dark logo** swaps in by CSS, on the selectors the colour tokens use, so it follows a
  visitor's toggle as well as their system. `<picture>` would have followed only the system.
- Public pages link the site's icon; the admin and the installer keep TomeCMS's, so the owner
  can tell the admin's tab from the site's.
- In Settings, each logo is previewed on the page it will be seen on -- the light one and the
  dark one, in either admin theme, on `--color-sample-light` and `--color-hero`, two roles
  that do not turn with it. A dark logo uploaded before a logo, or left when the logo was
  removed, stays in view there so it can be removed.

### Buttons that say they are working

- Every admin control that starts a request spins for at least 400 milliseconds, one number
  for the whole admin (`MIN_BUSY_MS`). A quick server answers a save in about fifteen: the
  Settings button was measured spinning for 14.6, which is one frame and reads as nothing
  having happened. A slower answer is not held back, and a failure waits the same minimum so
  its message does not flash in either.
- The places that did not keep the standard do now. Security spun every button for any one
  action, Copy included; the media library's Create folder, Save folder name and Save had no
  busy state and its Delete swapped its label; the menu's Save swapped its label and Retry
  spun beside it; Check again and Install on the update page, and the suggestion buttons,
  swapped theirs. Only the pressed button spins, and the words sit beside it, so no button
  changes width while it works.

### Documentation

- The system overview walks what is suggested while writing, as a guided view of its own, and
  says where a logo goes -- through the server, where a library image does not.

## Validation boundary

The same gates as 0.5.0, green on the commits this release contains, with no warnings left on
the CI run. The brand's storage is tested against the real object store on the disposable
stack, and the header's two logos by which of them the browser actually displays. Each guard
was checked by putting back the bug it guards against, and some of the plan's own checks were
found not to be checks before the code they cover was committed: a centring test that a
cropped icon also passed, and a path back out of the bucket that no test reached.

One unit test of the updater's command timeout races node's own startup under heavy parallel
load. It failed once in a full local run and passes alone and in CI; it is to be fixed
separately.

The release workflow can still be exercised only by tagging a release. What is required
before a production tag is unchanged from the
[0.3.0 notes](0.3.0.md#still-required-before-a-production-tag).
