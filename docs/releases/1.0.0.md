# TomeCMS 1.0.0

Date: 2026-09-28
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.0.0 is the first stable release. A fresh VPS now gets a managed install: the
installer runs the release's official image, verified against its attestations, and sets up an
updater with which the owner installs later releases from "System" in the admin. The first
update it supports is `1.0.0 → 1.0.1`.

From here, versions follow Semantic Versioning. A patch release only fixes, and a minor release
adds features without breaking what works, including the content API under `/api/v1`. The
feature freeze that began at 0.11.0 ends with this release.

## Upgrading

A 0.x install cannot become a managed 1.0.0 install in place, through the admin or by running
the installer over it. Make and verify a full backup, keep the old secrets somewhere private,
and install 1.0.0 on a separate fresh server. Move the content over by hand and check it there,
then switch the DNS. [Installing on a VPS](https://dhanabhon.github.io/tome-cms/start/install/#moving-from-0x)
walks through it.

A build from source, made with `scripts/deploy-vps.sh` from a checkout that is not a release
tag, still upgrades in place by running the helper again. There is no migration, no new setting
and no new runtime dependency since 0.14.1. Such an install only checks for updates, and reads
"TomeCMS 1.0.0 is available." under "System".

`deploy/cloud-init.yaml` now installs 1.0.0, which means the managed install, run as root from
`/opt/tome-cms-src`.

## Installing

- **The managed installer is the way to install.** Clone the release's tag, run `npm ci`, and
  run `scripts/install-managed-vps.sh --version 1.0.0` as root. It checks the release on
  GitHub, verifies the manifest and the image with `gh attestation verify`, pulls the image by
  its digest, and writes the secrets to `/etc/tome-cms/tome-cms.env`.
- `scripts/prepare-vps.sh` ends by printing those commands for the release it comes from.
- Run by root directly, or with `--user root`, `prepare-vps.sh` now names the options that fix
  it: `--create-user --user tomecms`, or `--user <name>` for an account that exists.

## Updating from the admin

A managed install runs `tomecms-updater`, a systemd service. When a newer stable release is
published, "System" offers "Install 1.0.1" (with that release's version). After the owner's
passkey, the updater checks the release the way the installer does, takes a full backup of
PostgreSQL and the bucket into `/var/backups/tome-cms/`, runs the migrations, restarts the
application and checks its health. [Updating](https://dhanabhon.github.io/tome-cms/running/updating/)
describes each step.

## The documentation

- Installing, updating, configuration, recovery and the first-run wizard describe the managed
  install first, and a build from source second.
- New: what to do without a domain yet, how to point DNS at the server, and how to prepare a
  server while logged in as root.
- The security policy supports the latest `1.x` release. The contributing guide takes features

## For theme authors, plugin authors and headless sites

Nothing a theme, plugin or headless site depends on changed since 0.14.1. From this release,
`/api/v1` changes only in ways that keep existing clients working, such as a new route or a new
field. A change that would break a client gets a new path, such as `/api/v2`.

## Supported update boundary

- The first supported web path is exactly `1.0.0 → 1.0.1` on a fresh managed VPS.
- Pre-`1.0.0`, local macOS/Windows, and source-built Compose installations remain check-only and need a manual transition.
- Routine web updates replace only the official TomeCMS application image by digest. PostgreSQL 17, SeaweedFS 4.46, Docker, TLS, DNS, and their data volumes are outside the transaction.
- Bundled and Headless installations use the same image and updater. `/api/v1/content/*` remains available in both modes; Headless mode continues to hide only the bundled public frontend.

## Release prerequisites

The `v1.0.0` and `v1.0.1` releases must be public, published, stable, and immutable. Each release must contain these exact assets with GitHub SHA-256 asset digests:

- `update-manifest.json`
- `update-manifest.attestation.json`
- `tomecms-image.attestation.json`

Both attestation bundles must verify against `Dhanabhon/tome-cms/.github/workflows/release.yml`, the exact release tag, and the manifest source commit. The installer and updater use downloaded bundles instead of GitHub's authenticated attestation API lookup, install no permanent GitHub credential, and reject self-hosted-runner attestations.

## Recovery boundary

The updater retains a complete PostgreSQL plus object-storage backup before selecting the target image or running a migration. If the target fails readiness, app-image rollback is automatic only when the release declares the previous version schema-compatible. No down migration runs.

Database and object restoration is deliberately manual. A failed job that cannot safely restore the previous image enters `failed_manual_recovery`, retains its backup, and blocks another web update. Do not delete `job.json`, remove volumes, run `down --volumes`, or regenerate secrets to bypass that lock.

Inspect the bounded status and private service log first:

```sh
sudo curl --unix-socket /run/tome-cms/updater.sock http://localhost/v1/status
sudo journalctl -u tomecms-updater -n 100 --no-pager
sudo less /var/lib/tome-cms/updater/job.json
```

Stop writers and copy the retained backup off-host before repair:

```sh
sudo systemctl stop tomecms-updater
sudo docker compose -p tomecms -f /opt/tome-cms/compose.managed.yaml \
  --env-file /etc/tome-cms/tome-cms.env \
  --env-file /var/lib/tome-cms/updater/image.env stop app
sudo find /var/backups/tome-cms -mindepth 2 -maxdepth 2 -name manifest.json -type f -print
```

Validate the selected recovery point in a uniquely named disposable restore project from a matching trusted checkout before changing production data:

```sh
npm run restore:check -- \
  --backup /absolute/path/to/retained/tomecms-backup \
  --project tomecms-restore-check-YYYYMMDD
```

Production database/object restoration has no generic one-command wrapper in `1.0.0`; it must be reviewed against the retained manifest and the failure point.

## Features intentionally absent from 1.0.0

- Automatic or scheduled updates
- Beta, preview, or custom release channels
- Automatic backup pruning
- Web-based updater self-update
- Web-based PostgreSQL, SeaweedFS, Docker, proxy, DNS, or TLS updates
- Automatic database/object restore or down migrations

Updater self-updates and every infrastructure update remain manual, separately reviewed operator work.

## Acceptance on real servers

The repository operation harness uses Docker Engine and Compose to build local `1.0.0`/`1.0.1` fixture images and start a real app HTTP server with pinned PostgreSQL 17 and SeaweedFS 4.46 services and named volumes. Through the real Unix updater server, state store, release verifier, and transaction, it delegates Compose stop/run/up/ps, the container backup and migration commands, readiness, inspection, app-image switch, rollback, and cleanup to Docker. The fixture backup contains schema-valid synthetic database and object bytes whose sizes and hashes are verified. Public GitHub downloads/attestation execution, immutable official-digest-to-local-image mapping, and migration-inventory discovery remain explicit external-boundary substitutes.

Every Docker mutation is guarded by one random `tomecms-test-*` project and a task-owned temporary root. Cleanup is registered before the first build or Compose operation, removes only exact labelled test resources, and verifies that no matching container, network, volume, image, or temporary root remains. The harness rejects the production `tomecms` project and fixed production paths.

```sh
npm run test:operations:update
```

CI runs it on every push to `develop`, on `linux/amd64`. It does not replace the runs below, which use the published `v1.0.0` and `v1.0.1` releases on disposable real servers and are recorded here, without secrets or Passkey material, as they are done:

| Gate | Architecture | Image digests | Migration key | Backup manifest SHA-256 | Updater | Readiness | Status |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Fresh install, update, and healthy restart | `linux/amd64` | — | — | — | — | — | Not performed |
| Intentionally unhealthy target and compatible rollback | `linux/amd64` | — | — | — | — | — | Not performed |
| Fresh install, update, and healthy restart | `linux/arm64` | — | — | — | — | — | Not performed |
| Intentionally unhealthy target and compatible rollback | `linux/arm64` | — | — | — | — | — | Not performed |

Each architecture starts from a fresh managed `1.0.0` install over HTTPS, completes the Wizard and Passkey enrollment, creates a Post, Page, Category, Navigation item, and media object, verifies an operator backup in a disposable restore project, then installs `1.0.1` and checks Admin, the selected frontend mode, media, API, and updater history.
