# TomeCMS 1.16.4

Date: 2026-10-06
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.16.4 closes the weaknesses the 1.16.3 security review set aside, and tidies the
recovery page. `/api/v1` is unchanged.

## Upgrading

- **A managed install** updates from "System" in the admin, as
  [Updating](https://dhanabhon.github.io/tome-cms/running/updating/) describes, or with
  `sudo tome update` on the server. There is no migration, so the updater backs up the database
  alone.
- **A build from source** upgrades in place by running the deploy helper again.
- **The updater** stays at 1.6.0. Nothing to upgrade on the server.
- **The media proxy needs one step.** A server prepared with `prepare-vps.sh` gets the new media
  protections below by running the script again from the release, in the folder the updater
  already uses:

  ```sh
  cd /opt/tome-cms-src
  git fetch --depth 1 origin tag v1.16.4
  git checkout --detach v1.16.4
  sudo ./scripts/prepare-vps.sh --cms-url https://cms.example.com --media-url https://media.example.com
  ```

  Use your own two addresses. Each step says whether it changed anything; this run rewrites
  `/etc/caddy/Caddyfile` and reloads Caddy. A proxy of your own takes the same three settings by
  hand, as [the reverse proxy](https://dhanabhon.github.io/tome-cms/start/requirements/#the-reverse-proxy)
  now lists.

`deploy/cloud-init.yaml` now installs 1.16.4.

## Security

- **Deleting or renaming a Passkey needs a recent check.** As adding a spare has since 1.16.3,
  the server only deletes or renames a Passkey for a session verified in the last five minutes,
  and the Security screen asks for a Passkey first. better-auth's own rename route, which
  TomeCMS does not use, is turned off, as its delete route already was.
- **A media link cannot turn a file into a web page.** The storage behind the media address obeys
  `?response-content-type=` and `?response-content-disposition=` on any request, so a link could
  serve a picture as HTML or open an SVG inline. The Caddy that `prepare-vps.sh` writes now drops
  those parameters, sends `nosniff` with every file, and sends a sandboxing
  `Content-Security-Policy` with every SVG, so a logo or icon opened at its own address runs
  nothing. TomeCMS's own uploads never used those parameters, and still work.
- **SVG logos and icons are stored as downloads.** They go up with `Content-Disposition:
  attachment`, which `<img>` and an icon link ignore; a restore puts it back. One stored before
  1.16.4 gets it the first time the updated app finds its database and storage ready.
- **The SVG sanitizer reads CSS more carefully.**
  - An `@import` cut in two by another (`@im@import x;port`) no longer grows back.
  - A style element's text goes out with its `&` escaped, so an entity in it is read once, as it
    was checked, rather than twice.
  - An SVG with an element inside its `<style>` is refused, since a nested style could hide CSS
    from the check.

  An SVG with an `&` in its CSS, which could not be drawn before, now can.

## Fixed

- **The recovery page.**
  - Its heading fills the column instead of wrapping early, and in Thai never breaks inside
    "พื้นที่ทำงาน".
  - The line under it no longer touches the heading's lowest vowels.
  - "Continue securely" sits on the code field's line rather than its label's.

## Testing

- **Unit:**
  - the SVG sanitizer: the split `@import`, double-encoded entities, an element inside a style,
    and an `&` in CSS that can now be drawn;
  - a restored SVG goes back as a download;
  - the Caddyfile `prepare-vps.sh` writes for the media origin.
- **Integration:**
  - a stale session can neither delete nor rename a Passkey, and better-auth's rename route
    answers 404;
  - SVG logos and icons are stored as downloads, and an older one is given the header once,
    keeping its type, cache rule and bytes.
- **Browser:**
  - an owner whose session is ten minutes old renames and deletes a Passkey after confirming
    one; without the screen's check, the test fails;
  - the Thai recovery page at 932 and 375 pixels: the heading keeps "พื้นที่ทำงาน" on one line,
    the hint stands clear of it, and the button sits on the field's line.
- **By hand, against SeaweedFS 4.46 behind Caddy 2.8:** a `?response-content-disposition=inline`
  request comes back `attachment`, an SVG comes back with the sandboxing policy, and a signed
  upload still goes through.
