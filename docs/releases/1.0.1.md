# TomeCMS 1.0.1

Date: 2026-09-28
Status: Stable release; tagged and published as a GitHub release

TomeCMS 1.0.1 fixes the managed installer, which could not finish on a real server in 1.0.0.
Install 1.0.1 on a fresh VPS. There was never a finished managed 1.0.0 install to update, so
the update path from the admin starts at `1.0.1 → 1.0.2`.

## Upgrading

- **A managed 1.0.0 install** does not exist: the installer stopped before writing any file,
  and removed what it had created. Run the 1.0.1 installer on the same server, from a clone of
  the `v1.0.1` tag, as [Installing on a VPS](https://dhanabhon.github.io/tome-cms/start/install/)
  shows.
- **A build from source** upgrades in place by running the deploy helper again. There is no
  migration, no new setting and no new runtime dependency.
- **A 0.x install** still needs a fresh server, as the [1.0.0 notes](1.0.0.md#upgrading) say.

`deploy/cloud-init.yaml` now installs 1.0.1.

## The managed installer

- **It finishes.** Before it writes anything, the installer lists the migrations inside the
  release's image, to check that the image matches the manifest. It ran `node --import tsx` in
  a container with a read-only filesystem, and `tsx` could not create its cache in `/tmp`, so
  the installer stopped at that step on every server. The container now gets a small
  in-memory `/tmp` and stays read-only everywhere else.
- **The updater had the same step,** and would have stopped an update from the admin in the
  same way. The installer and the updater now take the command from one place,
  `src/updater/inventory.ts`, so the two cannot drift apart.
- **A missing address is named.** Without `TOME_CMS_PUBLIC_URL` or `S3_ENDPOINT`, the
  installer fell back to the defaults for a local checkout and reported
  `TOME_CMS_PUBLIC_URL requires HTTPS without credentials`. It now says which one is not set.
- **Busy ports stop it before anything changes.** The installer checks that ports `5432`,
  `9000` and `4321` are free on `127.0.0.1`, in the dry run as well, with the deploy helper's
  own check. An earlier install on the same server holds them, and the Compose start that
  would have failed on them came after the installer had written its files.

## CI

The operations harness stands in for the step that broke, which is how 1.0.0 passed CI with
it. CI now builds the application image and runs that step against it with
`npm run check:inventory`, using the installer's own arguments, and fails unless the list ends
at the newest migration in the checkout.

## For theme authors, plugin authors and headless sites

Nothing a theme, plugin or headless site depends on changed.

## Validation boundary

- `npm run check` passes, and the documentation site's check and build pass.
- `npm run test:unit`: 592 tests, all passing, among them the new ones for the inventory's
  writable `/tmp` (installer and updater), the missing address, and a busy port.
- `npm run check:inventory` lists 26 migrations, ending at `026_planned_dates`, both on the
  published 1.0.0 image and on an image built from this code, on `linux/arm64`. With the 1.0.0
  arguments the same image fails with `ENOENT … mkdir '/tmp/tsx-1000'`, which reproduces the
  failure seen on the server.
- On 2026-09-28, on a DigitalOcean server (`linux/amd64`, Ubuntu 24.04) prepared with
  `prepare-vps.sh`, the 1.0.0 installer's dry run passed every check against the real GitHub
  release: the release's immutability and asset digests, and `gh attestation verify` of both
  the manifest and the image. The full run then stopped at the migration inventory, and the
  server was left with no file, account, container or volume from it.

The four acceptance rows in the [1.0.0 notes](1.0.0.md#acceptance-on-real-servers) move to
this release: a fresh managed `1.0.1` install, then an update to `1.0.2`, on `linux/amd64` and
`linux/arm64`.
