# TomeCMS 0.14.1

Date: 2026-09-28
Status: Release candidate; tagged and published as a GitHub release, not for production

TomeCMS 0.14.1 is 0.14.0 with fixes to the server preparation script, a link in the admin
footer, and CI that tests each commit once. The one change in the application is the link.

This is still a pre-1.0 release candidate. A 0.x site upgrades in place when the deploy helper
is run again from a newer checkout.

## Upgrading

There is no migration, no new setting and no new runtime dependency. A site on 0.14.0, 0.13.0
or 0.12.1 reads "TomeCMS 0.14.1 is available." under "System" once this release is published.

An installation created from a version earlier than 0.11.0 still needs what the
[0.11.0 notes](0.11.0.md#upgrading) list.

`deploy/cloud-init.yaml` now installs 0.14.1. A server created from the 0.14.0 file ran the
0.14.0 script, without the checks below; nothing on it needs to change.

## Preparing a new server

- **Signing keys are pinned.** Before `scripts/prepare-vps.sh` adds the apt repository of
  Docker, NodeSource, the GitHub CLI or Caddy, it checks that the signing key it downloaded
  carries the fingerprint the vendor publishes. A different key stops the script, and nothing
  is added to the server.
- **SSH key options are kept.** The account `--create-user` makes gets root's SSH keys with
  their options, such as `from=` and `restrict`. Only the "log in as ubuntu" command a cloud
  image puts in front of root's keys is dropped. In 0.14.0 every option was dropped.
- A failing step reports its error once, and a failed install leaves no temporary file.
- A unit test keeps the repository address in the script and in the cloud-init file the
  official one.

## The admin

"TOMERA Co., Ltd." in the footer of every admin page links to [tomera.ai](https://tomera.ai),
in a new tab.

## Releasing

CI runs on `develop` and on pull requests, and no longer on `main`. A merge into `main` is a
fast-forward of a commit CI has already run on, so `tag-release.yml` starts from the push to
`main`, waits for CI to pass on that same commit, and only then tags it and starts the release.
A commit CI never ran on, such as a merge commit or a fix pushed straight to `main`, is not
released. This is the first release made that way.

The history of `main` and `develop` was rewritten to take out the `Co-Authored-By` lines in
older commit messages. The files are the same. The tags of earlier releases still point at
their original commits, so their attestations are unchanged.

## For theme authors, plugin authors and headless sites

Nothing a theme, plugin or headless site depends on changed.

## Validation boundary

- `npm run check` passes, and `shellcheck` reports nothing on the script.
- `npm run test:unit`: 587 tests, all passing.
- The browser test for the admin footer passes.
- In an `ubuntu:24.04` container on `arm64`, the script installed all four packages through
  the fingerprint check, refused a key whose fingerprint did not match without writing
  anything, and kept the options on root's SSH keys for the new account.

Neither server tool has yet been run on a real server. That belongs with the acceptance on the
two real HTTPS servers, `linux/amd64` and `linux/arm64`, that the
[road to 1.0.0](../plans/2026-09-24-road-to-1.0.0.md) names, still to be done before 1.0.0.
What is required before a production tag is unchanged from the
[0.3.0 notes](0.3.0.md#still-required-before-a-production-tag).
